Two things got done this session and one thing got un-done. Read the un-done
part first, because a previous commit message states it wrongly and the docs
now contradict that commit.

---

## ⚠ Start here: a claim from this session is retracted

Commit `fd65be0` says the memory corruption's root cause is
`cedrus_stop_streaming()` freeing DMA buffers without halting the VE. **That is
not established.** A one-hour soak of the full configuration — IOMMU
translating both VE ports **and** `sunxi_cedrus.stop_reset=Y`, i.e. both
mitigations active — crashed after **390 seconds**:

```
Internal error: Oops - Undefined instruction: 0000000002000000 [#1]  SMP
CPU: 3  PID: 3266  Comm: kworker/u16:2
Workqueue:  0x0 (pan_js)          <- work function NULL, as in the very first crash
pc : __schedule+0x284/0x794
```

The retraction is in `e396571` and at the top of the relevant section in
`docs/vaapi-scope.md`. The mistake to learn from: the A/B that "established"
the root cause was **one run per arm**, against a bug whose crash latency
ranges **113 s to 848 s**. A single clean 450 s arm never had the power to carry
that conclusion.

**Anything in this repo asserting a cause for the corruption should be read as a
hypothesis until it survives a soak of an hour or more.**

## What is solid

### 1. Stock ffmpeg and mpv decode H.264 on the VE — 5/5 bit-exact

The session's original goal, done and reproducible from a cold boot.
`patches/libva-v4l2-request/` carries three patches on the pinned head of
bootlin's PR #38. Build them **on the board** (`meson setup build && ninja -C
build`) — the driver's entry point is `__vaDriverInit_<major>_<minor>` taken
from the libva version at build time, so a host build against a different libva
produces a `.so` the board's loader silently ignores.

The one that mattered was patch 0003: ffmpeg allocates VA surfaces on demand and
passes **no** render targets to `vaCreateContext`, so the shim created a
zero-buffer bitstream queue and `STREAMON` failed with `EINVAL`. The error named
the codec; the codec was fine. `strace` found it in one run.

Gate: `/root/video-test/va-decode-test.sh` (scores a software control first, so
a hardware mismatch can never be confused with a broken yardstick).

### 2. The H713's IOMMU is driven by mainline for the first time

`patches/kernel/0041` (driver) + `0042` (DTS), documented in
`docs/iommu-port.md`. Verified on hardware: probes, `BYPASS` reads `0x7C`
(masters 0 and 1 translated), decode stays **5/5 bit-exact through translation**.

Everything about the block was measured, not inferred — the vendor DTB from
**board B's own eMMC**, the register map from the vendor `vmlinux`'s
disassembly, and the block's own registers read over `devmem`. `docs/iommu-port.md`
has the full account including the `of_xlate` reverse-engineering that
established what the second DT cell means (1 = translate, 0 = leave bypassing).

**Two traps worth not re-discovering:**

- **The VE has two IOMMU master ports.** The stock tree declares `ve@1c0e000`
  and `ve1@1c0e000` — same block, same address, masters 0 and 1. Attaching only
  master 0 gives an IOMMU that probes, enables, installs a page table, reports
  **no faults at all**, and decodes **corrupt**: half the traffic follows the
  IOVAs and half bypasses to physical. Nothing touches an unmapped IOVA, so
  there is nothing to fault on.
- **The H713 node has no reset line.** Mainline required one; probe failed with
  `-ENOENT` and cedrus silently fell back to dma-direct. 0041 makes it optional.

Patch 0041 leaves H6/H616 behaviour untouched and is close to upstreamable. The
open question before submitting is the binding: vendor `#iommu-cells = <2>`
against mainline's `<1>`.

## The open problem

**Kernel memory corrupts when a CMA-backed KMS scanout runs.** Hardware decode
was thought to be required; it is not — see "The control ran" below, which
crashed with the video engine at zero interrupts. Six-plus different victims
across runs — a `pool_workqueue`,
the hrtimer rbtree, a `dma_fence`, the deadline runqueue, a kernel stack, the
CFS scheduler. Different site every time is the signature of corruption, not of
a code race, and it is why `drm_sched_run_job_work` kept appearing: it is simply
the hottest code during playback, so it trips over whatever was scribbled on.

### What is ruled out, with evidence

| ruled out | how |
| --- | --- |
| **VA-API / mpv / ffmpeg / the shim** | reproduces with **zero VA-API**: GStreamer `v4l2slh264dec` → `fakesink` plus mpv doing *software* decode to the panel still corrupts (`docs/reference/expE-no-vaapi-still-crashes.log`) |
| **A drm_sched teardown race** | different faulting site every run; and `cma=` changes the symptom, which a code race cannot care about |
| **A bounded overrun past the capture buffer** | the `dma_guard` in patch 0039 (arm with `sunxi_cedrus.dma_guard=65536`) reports **nothing**, and the victims are slab/stack, which CMA never hosts because they are unmovable |
| **CMA exhaustion / buffer leak** | `CmaFree` flat at 93,600 kB through a full run, released on exit |
| **Height alignment (16 vs 32 rows)** | a 32-aligned 1280x736 clip crashed *sooner* (113 s vs 457 s) |
| **An upstream fix we are missing** | `drm_sched_is_stopped()` in current master is literally `READ_ONCE(sched->pause_submit)`; the panfrost `timeout_wq` fix is already in our tree |

### The control ran — cedrus is exonerated (2026-08-17, later the same day)

Experiment 1 below was run. **It crashed, with the video engine at zero
interrupts.** Full account in `docs/vaapi-scope.md` under "Experiment I", trace
in `docs/reference/expI-display-only-no-ve-crashes.log`.

`mpv --hwdec=no` to the panel, same `6.18.38-builtin` kernel, same `cma=128M`,
no IOMMU, cedrus never opened: 32 consecutive heartbeats with `ve=0`, then

```
[ 1008.405737] Workqueue:  0x0 (pan_js)
[ 1008.405862] Kernel panic - not syncing: kernel stack overflow
```

The `ve=0` count is positive proof rather than an assumption — cedrus is built
into that kernel and cannot be removed, so a flat interrupt count from boot to
panic means no frame ever reached the engine. One counterexample is enough to
refute a *necessity* claim, which is why this does not repeat the mistake the
retraction was about.

So the sentence "the necessary and sufficient ingredients are cedrus decoding
into CMA buffers, concurrently with a KMS/GBM scanout from CMA" is now half
false. **Cedrus's missing reset may still contribute** — with the fix off the
crash came faster — but it is not required.

Taken with run D (hardware decode *and* GPU rendering, scanout from the reserved
carveout, clean over 480 s), the discriminating variable across every run on
record is **where the scanout buffer lives**, not what feeds it.

Two further narrowings from the same run:

- **Not DECD.** Its `jiffies_hist[jpos + 2]` overrun into an adjacent
  `work_struct` (patch 0034) would have been the perfect explanation for a NULL
  work function, but `-builtin` has no module tree, DECD is a module, and its
  `"decd"` interrupt is absent from the run's baseline. The live display path
  was the AFBD KMS driver, panfrost and `sunxi-scanout-dmabuf`.
- **The corrupting write has a shape.** `sp : 0000000081350040` against a task
  stack of `[0xffff800081350000..0xffff800081354000]` — the pointer's **upper 32
  bits were zeroed and its low half left intact**. That is a 32-bit write onto
  the high word of a 64-bit pointer, not an arbitrary smear.

### Next experiment

**Attach the display to the IOMMU** — `iommus = <&iommu 2 1>` on the AFBD node —
and soak. This departs from the vendor's configuration, so it is an experiment
rather than a fix, but it would turn a stray write into a named fault. It is now
the primary experiment rather than the fallback.

Two things checked while the control ran, both of which affect how to do it:

- **Master 2 is shared.** `docs/iommu-port.md` puts `ge2d@5240000` *and*
  `dec@5600000` on `<&mmu_aw 2 0>`. Nothing in our tree drives ge2d, so the
  attachment is unambiguous, but master 2 is not the display alone.
- **It should not need driver work.** The AFBD KMS driver takes its scanout
  address from `drm_fb_dma_get_gem_addr()`, so under translation it programs an
  IOVA and keeps working. The exception is `sunxi-scanout-dmabuf`, which hands
  out physical addresses from the `0x6c100000` carveout by design — that path
  (`gles-play`) will fault once master 2 translates. mpv's GBM path is
  unaffected.

## Operational knowledge earned this session

- **`oops=panic` on the command line is the single biggest time-saver.**
  `panic=5` is already there, so every crash self-reboots in five seconds
  instead of hard-locking. It removed the human power cycle from the loop
  entirely — three were needed before it, none after.
- **WiFi cannot carry a file on this board.** Twice out of two, a sustained
  transfer wedged it hard enough to take the serial console with it. The second
  attempt is the diagnostic one: a 10.8 MB `scp` sat at **zero bytes for six
  minutes** with the board responsive, then `cmd timed-out` (the aic8800
  firmware crash path) and it died. Use it for a shell and log reading only;
  files go over serial (`tools/serial/send_file.py`) or into the rootfs image.
  `tools/wifi/sta-connect.sh` sets the link up and carries this warning.
- **A FIT transfer is 12–17 minutes** at 10.8 KB/s (`tools/serial/load_fit.py`,
  then `fatwrite mmc 1:2 0x50000000 <name>.fit $size` to make it permanent).
- **`tools/serial/reboot-to-uboot.py`** reboots and types through the autoboot
  delay. Give it 70 seconds — a debug kernel's shutdown can outlast 40.
- **DRM card numbers swap** between module and built-in kernels. Production:
  `card0` panfrost, `card1` AFBD. Debug kernels (drivers built in): the reverse.
  Check before passing `--drm-device`.
- **`/tmp` is a 467 MB tmpfs.** A 1080p vector decodes to 186 MB; ENOSPC leaves
  a truncated file with a valid md5, which scores as MISMATCH and reads as a
  decode bug. `va-decode-test.sh` writes to `/var/tmp` for this reason.
- **The board's clock drifts backwards across power cycles**, and `meson setup`
  aborts with `Clock skew detected`. `date -u -s` from the host, then
  `hwclock -w`. The RTC is not holding, despite `rtc-timekeeping-bringup`.
- **`sysrq` does not rescue a hard lockup here** (`tools/serial/sysrq.py`, and
  `MAGIC_SYSRQ` is in both debug fragments). With every CPU spinning
  interrupts-disabled nothing runs the handler. Keep it for softer hangs.

### Debug kernels available

`KERNEL_CONFIG=<name> build/build.sh kernel` merges
`patches/kernel/board/<name>.config` and produces `h713-kernel-<name>.fit`.
Fragments are part of the input digest, so a debug build gets its own tree and
cannot overwrite the production FIT.

| fragment | for |
| --- | --- |
| `kasan` | KASAN. Note it **hides this bug** — 24 min / 42,773 frames clean, and no report either, because the writer is a device and KASAN instruments CPU accesses |
| `builtin-drivers` | the four suspects built in, no KASAN — the control that showed KASAN was masking it |
| `iommu` | the IOMMU live, cedrus translated |

Runtime knobs (no rebuild): `sunxi_cedrus.dma_guard=<bytes>` (patch 0039, pads
and poisons capture buffers), `sunxi_cedrus.stop_reset=0|1` (patch 0040, halts
the VE before freeing its buffers; **writable at runtime**, which is what makes
same-boot A/B possible — just remember one run per arm is not enough).
