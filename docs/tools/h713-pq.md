# h713-pq — turning stock picture data into register arguments

`h713-pq` reads the HY310's own picture-quality (PQ) data — extracted from *your* device, never shipped —
and computes the RPC arguments and gamma LUTs the kernel and `h713-tv` need. It opens no device, writes no
register and talks to no board: everything it produces is a number, a JSON object, or a LUT file, and the
actual write happens elsewhere (the kernel, or `h713-tv` at startup).

## Who needs it, and when

`h713-tv` runs it once as a child process at every start (`show … --json --lut …`) so the nine picture
controls and the gamma curve it applies come from your device's own data instead of a table frozen at build
time — one calculation, not the same arithmetic duplicated in C. You would run it by hand to inspect what a
preset contains, to get a saturation RPC argument for a manual test, or to regenerate a gamma LUT file:

```bash
h713-pq --daten /etc/h713/tvconfig show HDMI1 standard --json --lut /run/h713-tv/gamma-laufzeit.bin
h713-pq saturation HDMI1 cinema      # -> RPC argument for one preset
h713-pq gamma 2.2 --lut gamma.bin    # DE2 LUT from a gamma exponent alone
```

Without `--daten`, it searches `$H713_TVCONFIG`, then `/etc/h713/tvconfig`. It needs only the Python 3
standard library (tested with 3.12) — no package, no install step.

## The chain, and what is proven where

```
input × picture mode  →  user value 0..100  →  RPC argument 0..100  →  register (the firmware computes this)
```

The five PQ registers (brightness, contrast, saturation, hue, sharpness) take the RPC argument unchanged —
measured on hardware, `doku/nachtlog/K5-board-verifikation.md`. Saturation is the one exception: it also
writes a second, chroma-gain register as `floor(argument × 1.28)`, measured at five points (0/50/59/60/100 →
`0x00/0x40/0x4B/0x4C/0x80`). The step from **user value to RPC argument is not measured** — only what sits on
either side of it is — but it changes nothing observable in these vendor files: the factory curve that could
occupy that step disagrees with a straight pass-through at exactly one user value (75), and no preset here
uses it. That gap is documented, not resolved — a test locks in that it stays harmless.

The gamma LUT format (three 512-entry DE2 banks, one per channel) is fully proven, cross-checked byte-for-byte
against the legacy C++ reference (`tests/legacy_ref.cpp`) for every exponent it ships. On this device the
white-balance and gamma-point tables are neutral/empty, so `h713-pq gamma` works from the exponent alone; a
device with real values there would need the model extended, not just re-run.

## Limits

`h713-pq` computes and prints — it never opens `/dev/mem`, never SSHes anywhere, and never assumes a write
succeeded. The picture-mode **number** it sends is the firmware's own numbering (0 Vivid, 1 Standard, …),
which agrees with none of the three numbering schemes in the vendor files themselves — that table is a
measured fact (`doku/nachtlog/S14-re-picture-mode.md`), not a guess. `--json` reads only the three files a
preset needs; every other subcommand reads all eight and is slower for it.
