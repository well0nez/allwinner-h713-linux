# h713-pq - turning stock picture data into register arguments

`h713-pq` reads the HY310's own picture-quality (PQ) data - extracted from *your* device, never shipped -
and computes the RPC arguments and gamma LUTs the kernel and `h713-tv` need. It opens no device, writes no
register and talks to no board: everything it produces is a number, a JSON object, or a LUT file, and the
actual write happens elsewhere (the kernel, or `h713-tv` at startup).

## Who needs it, and when

`h713-tv` runs it once as a child process at every start (`show … --json --lut …`) so the nine picture
controls and the gamma curve it applies come from your device's own data instead of a table frozen at build
time - one calculation, not the same arithmetic duplicated in C. You would run it by hand to inspect what a
preset contains, to get a saturation RPC argument for a manual test, or to regenerate a gamma LUT file:

```bash
h713-pq --data /etc/h713/tvconfig show HDMI1 standard --json --lut /run/h713-tv/gamma-laufzeit.bin
h713-pq saturation HDMI1 cinema      # -> RPC argument for one preset
h713-pq gamma 2.2 --lut gamma.bin    # DE2 LUT from a gamma exponent alone
h713-pq curves 60 --source tse       # OSD value -> register, ini and TSE side by side
h713-pq gamma --from-tse normal --channel r --lut bank.bin    # the board's own curve, one bank
```

`--lut` writes as many DE2 banks as `--channel` asks for, and `h713-tv -g` takes exactly one: `--channel r`
gives 2048 bytes and is the file to hand it, `--channel all` gives 6144 bytes - three banks back to back -
and is for inspection, not for `-g`. To put a board's own curve on the wall, write the single bank over the
one `h713-tv` loads and restart it (keep the original, it is the shipped exponent-2.2 curve):

```bash
cp /usr/local/share/h713-tv/gamma-standard.bin /usr/local/share/h713-tv/gamma-standard.bin.orig
h713-pq gamma --from-tse normal --channel r --lut /usr/local/share/h713-tv/gamma-standard.bin
systemctl restart h713-tv@video3          # your instance number - never assume it
```

Done that way on the HY310 on 22.09.2026: the synthetic bank came out byte for byte equal to the shipped
`gamma-standard.bin`, and the TSE bank showed **no visible difference** on the wall - all three end points
are 4092 there, so only the curve's shape changes (`docs/subsystems/pq.md`).

The last two read the vendor's firmware database. On a device it is at `/boot/mips` - that is where
`h713-extract` puts `boot/mips/*` and where the installer writes it (`hy310-boot`, mounted at `/boot`),
so nothing has to be extracted for this. Elsewhere pass `--tse FILE-OR-DIRECTORY` or set `$H713_TSE_DIR`;
`--project 0x0034` picks another board's `ProjectID_0x00NN.TSE` out of a directory, the default `0x0030`
is the HY310's.

Without `--data`, it searches `$H713_TVCONFIG`, then `/etc/h713/tvconfig`. It needs only the Python 3
standard library (tested with 3.12) - no package, no install step.

## The chain, and what is proven where

```
input × picture mode  →  user value 0..100  →  RPC argument 0..100  →  register (the firmware computes this)
```

The five PQ registers (brightness, contrast, saturation, hue, sharpness) take the RPC argument unchanged -
measured on hardware, `doku/nachtlog/K5-board-verifikation.md`. Saturation is the one exception: it also
writes a second, chroma-gain register as `floor(argument × 1.28)`, measured at five points (0/50/59/60/100 →
`0x00/0x40/0x4B/0x4C/0x80`). The step from **user value to RPC argument is not measured** - only what sits on
either side of it is - but it changes nothing observable in these vendor files: the factory curve that could
occupy that step disagrees with a straight pass-through at exactly one user value (75), and no preset here
uses it. That gap is documented, not resolved - a test locks in that it stays harmless.

The gamma LUT format (three 512-entry DE2 banks, one per channel) is fully proven, cross-checked byte-for-byte
against the legacy C++ reference (`tests/legacy_ref.cpp`) for every exponent it ships. The **curve** inside
it is a different question: ours is computed and identical on all three channels, the vendor's is measured
and lives in the board's `ProjectID_0x00NN.TSE`, one per colour temperature, with the white balance in the
per-channel end points. On a HY310 those end points are all 4092 and the difference is a shape; on a HY300
Pro they are not, and our curve discards that board's white balance outright. `--source tse` gives the
vendor's curve and is **off by default** until a device test says otherwise - see the tool's README,
"Where the gamma curve comes from".

## Limits

`h713-pq` computes and prints - it never opens `/dev/mem`, never SSHes anywhere, and never assumes a write
succeeded. The picture-mode **number** it sends is the firmware's own numbering (0 Vivid, 1 Standard, …),
which agrees with none of the other three numberings for the same names - `tvpq.db`'s own row index,
libtvpq's `PQ_PICTURE_MODE` enum and libvideo.so's; all four are in the tool, kept apart by a test.
`--json` reads only the three files a preset needs (and no TSE at all); every other subcommand reads more
and is slower for it.
