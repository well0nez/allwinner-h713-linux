# h713-tv - the HDMI input as a running service

`h713-tv` is what puts a picture on the projector: while a signal is present on the HDMI input, the source's
image is shown on the wall; the moment the signal drops, the panel goes back to the Linux console, with no
manual step in either direction. A UNIX-socket control channel, `h713-tv ctl …`, reads and sets every picture
control, the volume, the aspect fit and the firmware's picture mode from a shell. Since 08.09.2026 the HDMI
audio path follows the same picture/no-picture state, muting itself when there is nothing to show - and since
22.09.2026 a picture drawn by the keystone warp counts as a picture too.

## Two devices, one job each

| Device | On this board | Role |
|---|---|---|
| `/dev/videoN` (`sun50i-h713-hdmirx`) | varies - `video1` or `video3`, whichever the driver got | says *whether* a signal is present and reports *when that changes* (`V4L2_EVENT_SOURCE_CHANGE`) |
| `/dev/dri/cardN` (`sun50i-h713-afbd`) | `/dev/dri/card1` | shows the picture: overlay plane in `hdmi-ring` mode reads the firmware's capture ring directly |

Neither number is hardcoded: both devices are found by matching driver/name against sysfs, the same approach
the udev rule below uses. Pixels never pass through this program - the plane reads the ring itself, `h713-tv`
only tells it to start and stop.

## Starting: a template unit, not `systemctl enable`

The unit is `h713-tv@videoN` - one instance per capture device - with no
`[Install]` section: the capture device can take over ten seconds to appear (the EDID/HPD sequence), so a
`multi-user.target` start would just race it. A udev rule starts the instance once the device exists:

```
SUBSYSTEM=="video4linux", ACTION=="add", ATTR{name}=="sun50i-h713-hdmirx",
    TAG+="systemd", ENV{SYSTEMD_WANTS}+="h713-tv@%k.service"
```

`BindsTo=dev-%i.device` ties the unit to the device both ways: it stops cleanly if the node disappears
(driver unbound) instead of hitting its restart limit, and udev starts it again once the device returns.
Verified 08.09.2026 with `udevadm trigger --action=add`, and again on 12.09.2026 when the camera happened to
enumerate first: the receiver landed on `/dev/video3` and udev started `h713-tv@video3` - **never assume a
number**. Manual start works too: `systemctl start h713-tv@video3`, or run
`/usr/local/sbin/h713-tv` in the foreground (Ctrl-C exits cleanly, plane off, console back). On an image with standby the receiver is unbound and bound again at every wake, and the instance is started again on whatever node it then finds ([below](#after-a-standby)).

### Startup options

```
h713-tv [-d /dev/videoN] [-c /dev/dri/cardN] [-s SOCKET] [-p PRESET] [-g LUT] [-a AUDIO] [-t DB] [-C CONFIG] [-n]
```

| Flag | Meaning |
|---|---|
| `-d`, `-c` | override device search (capture, DRM) |
| `-s` | control socket, default `/run/h713-tv/ctl` |
| `-p` | picture preset at start (`standard cinema vivid game computer hdr`, plus `energy_saving` and `custom` when the vendor data is present - the normal case - or `none`), default `standard` |
| `-g` | CRTC gamma LUT file (2048 B DE2 bank) or `none`. It beats the board's own curve and the computed one (below); without it nothing has to be given |
| `-a` | audio at start: `auto` (follow picture, default), `on`, `off`, or `none` (touch no ALSA card) |
| `-t`, `--hdmi-trim DB` | fixed HDMI-vs-device level trim in the audio DSP, 0 (default) to −100 dB |
| `-C` | config file, default `/etc/h713/tv.conf` (§ below) |
| `--data DIR`, `--calculator PATH`, `--input NAME`, `--lut PATH` | where the vendor data is, which program computes the picture values (`h713-pq`), which input it is asked about, where it writes the gamma curve. Each one overrides the `tv.conf` key of the same name; `none` for the first two switches the vendor data or the computation off |
| `-n` | report what was found and exit; the display and audio are left untouched |

### Where the gamma curve comes from

At start `h713-tv` asks `h713-pq` for the curves **this panel** was measured with: the board's own
`ProjectID_0x00NN.TSE` out of `/boot/mips`, all the colour temperature states it holds (normal, cool and warm on the
HY310 and the HY300 Pro), unchanged (`h713-pq gamma --export-slots`). Which ProjectID belongs to this board cannot be
read off `/boot/mips` - all 13 of them lie there - so it is told: `/etc/h713/board` (`project_id = 0x30`), which
`h713-install` writes out of the board profile. Without that file the device tree decides (`magcubic,hy310` -> `0x30`,
`magcubic,hy300-pro` and `magcubic,hy200-qz713df-a1` -> `0x34`), and if any step fails - no board file, no TSE,
`h713-pq` unhappy - the curve shipped with the program applies exactly as before, with one journal line naming the
step, and the two controls below say that they are not available and why.

What turns those raw curves into the curve on the CRTC's `GAMMA_LUT` is computed in the program (`gamma.c`), the way the
display firmware's own picture library does it ([below](#gamma-and-colour-temperature)). `ctl status` says which
curve is up, which level and colour temperature it is and what is on the CRTC:

```
gamma curve     computed here from this board's own curves (ProjectID 0x30)
gamma           level 3 (2.2), colour temperature auto (normal); curves of ProjectID 0x30: normal cool warm
                on the CRTC: normal, level 3, curve 9c4ce1af (32.7 ms, 1 sent, 0 refused)
```

What this buys is the **shape** of the panel's curve and, with it, the white balance a board bakes into the end
points of its curves: all three channels keep their own curve (on the HY300 Pro the end points are 4087/3863/3459 in the
warm state), on the HY310 all three end points are 4092 and the shape is the whole difference. `-g` beats all of it.

## `h713-tv ctl` - the control channel

The daemon listens on the socket from `-s`; a command is one line, and the reply's first word is `ok` or
`error`, so the exit code is decided without parsing further.

| Command | Does |
|---|---|
| `status` | last-known state: mode, signal, plane/console/warped, buffer, picture values, gamma curve, audio, plus the kernel and `cpu_comm` counters and the ARISC's EDID block mask. Reads the audio controls and two MSP sysfs files back, which ask the firmware: about 55 ms in the single-threaded daemon |
| `status brief` | the same without anything read back (8 ms): what the settings page polls, and what anything that polls should use - a full status every few seconds held the warp's frames 40-55 ms (23.09.2026) |
| `auto` (alias `on`) | picture follows the signal - the default without `tv.conf`, and the mode to stay in: switching by hand is where the rough edges are |
| `off` | force the console, until `auto` |
| `console` | un-blank the console and show the cursor, without touching the plane |
| `list` | every picture control of the capture node, with value and range |
| `get CONTROL` | read one control |
| `set CONTROL VALUE` | set one control; menus also take text (`set mode cinema`). Also the panel's `gamma` (0..4) and `colour_temperature` (auto, normal, cool, warm), see "Gamma and colour temperature" below, and the firmware's white balance (`wb_r_gain wb_g_gain wb_b_gain wb_r_offset wb_g_offset wb_b_offset`, 0..1023, 512 neutral) and colour management (`cm_AXIS_hue`, `cm_AXIS_sat`, `cm_AXIS_value`, -255..255, 0 neutral), see "White balance and colour management" below |
| `wb [R G B RO GO BO\|reset]` | the six white balance values: show, set all six in one call, or back to 512 |
| `cm [AXIS [H S V]\|reset]` | colour management: the entries that are not 0, one axis, the three values of an axis in one call, or everything back to the picture mode's own |
| `preset NAME` | send a manufacturer preset: picture mode plus its nine controls; discards unsaved deviations |
| `save [off]` | remember the current nine controls, preset, aspect, zoom, the six white balance values, the colour management steps that are not 0, the gamma level and the colour temperature; `off` deletes the saved file |
| `aspect [NAME]` | fit the source into the panel (`auto proportional full 16:9 4:3`); no name shows the current one. The firmware's `zoom` is refused - it stops the picture for good (06.10.2026) |
| `zoom [off\|in F]` | the digital zoom: `in` enlarges the centre by a factor 1.0…4.0 (default 2), `off` is the baseline; no argument shows it. Refused while the keystone warp draws (below). `out` is gone since 23.09.2026: the DE scaler only enlarges (a smaller destination window left its ratio at unity and showed a crop, measured at 0x05180008); shrinking the projection area is `h713-warp ctl zoom`, the GPU, as the vendor does it |
| `warp [status]` | whether `h713-warp` holds the video plane (drawing the ring or a Wayland client), with its commit counters. Running the warp, stopping it and setting the corners are `h713-warp ctl`, not this |
| `source [hdmi\|client\|auto]` | what the panel shows - the mode: the HDMI input; a program, a Wayland client drawn by `h713-warp` (Kodi under cage) - set by every mode unit's start, never the ring: h713-warp keeps the last picture while the program starts and between two programs, and puts the source back to `auto` once the program has ended (17.10.2026, measured on the HY310: see h713-warp); or the client while there is one and the input otherwise. A change gives a standing warp claim back only when the new policy forbids it (a ring claim under `client`, a client claim under `hdmi`) and h713-warp switches it; a claim that is allowed stands and h713-warp hears the new policy at once (`note source auto`), and `client` said again is a program that starts (`note source client`); under `client` without a warp claim the console stands until the client's first picture, and the HDMI sound is meant to be silent while a client is on the panel (not measured: the sources of the test runs sent no sound). Not saved; `tv.conf` `source =` is the start value (default `hdmi`; the image of the profile `desktop` sets `auto`, so that a restart of h713-tv keeps Kodi on the panel). See [h713-warp](h713-warp.md), "A Wayland client" |
| `audio [on\|off\|auto]` | force audio on/off or let it follow the picture (default); no argument shows the current policy |
| `volume [0..100]` | the volume on the stock curve (0 = the floor, 1 = -41 dB, 50 = -22 dB, 100 = -9.5 dB): in the DSP, where it mixes HDMI and the device sounds, else in the codec's DAC; no number shows it |
| `mute [on\|off]` | the DSP's master mute (HDMI and device sounds) plus the codec's own switch; no argument shows the current state |
| `resync` | re-select the source (`SetSource HDMI-1`) |
| `replug` | play an unplug/replug cycle to the source (HPD down 300 ms, EDID reload, HPD up) - blocks about 1 s. Since the kernel patches `0136a`/`0136c` (16.09.2026) a freshly plugged source keeps its picture by itself; keep this for an image older than that, or for a source that refuses to re-lock |
| `edid block0\|block1` | a replug that publishes that half of `/lib/firmware/hy310-edid.bin` to the source (`S_EDID` with two blocks, kernel `0170`). `block1` is the vendor's HDMI 2.0 set, which on the HY310 adds 1080p100/120 - both in the firmware's table - and 4K50/60, which are not; `tv.conf` `edid =` makes it the standing setting. Since 11.10.2026 every half this program publishes puts the panel's own CTA timing first when the file's first timing is larger than the panel (`edid_prefer = panel`, the default; `file` keeps the file's order): a source that follows the EDID then sends the panel's resolution, which on the 720p boards avoids the firmware's downscaling ring and its frame loss ([known issues](../known-issues.md)). `status` names the half in force, the VICs it offers that the firmware's table does not carry, and the timing put first. Every EDID this program publishes, by `edid`, by `replug` or at start, also loses its Deep Colour bits (see below), and `status` says `no deep colour offered` or names the bits still on |
| `hdcp` | the five HDCP lines alone: the version negotiated, authenticated or not, the 1.4 and the 2.2 key, and the firmware's last HDCP log line (sysfs `hdcp`, kernel `0174`; `status` shows the same) |
| `rpc NAME [ARG…]` | a raw call into the firmware over `cpu_comm`; the driver checks nothing for you |

### `zoom`: three verbs, and who scales what

**Bench-tested on 22.09.2026 (HY310, test pattern and camera); the model is in
[display](../subsystems/display.md).**

Nothing on the ARM side scales. What zooms is the display firmware, and it is told so through two windows
of the descriptor - the part of the source it reads and the part of the capture ring it writes - which the
kernel offers as the plane properties `src-window` and `dst-window` (patch `0133f`, in panel pixels). The
plane's own rectangle is only the placement on the panel.

- `ctl zoom in 2` - the source window becomes the centre quarter of the frame and the firmware blows it up
  into the whole ring; the plane stays over the whole panel. Measured: the centre quarter filled the panel
  and the test pattern's cell pitch doubled. A factor is any number from 1.0 to 4.0.
- `ctl zoom out P` - **gone since 23.09.2026**. The DE's picture scaler only enlarges: a smaller destination window
  left the ratio at unity and the firmware put the top left crop into it (measured at 0x05180008). Shrinking the
  projected picture is `h713-warp ctl zoom`, which does it inside the keystone matrix as the vendor does.
- `ctl zoom off` - neither window, the plane over the whole panel: the baseline.

`ctl status` names both windows and the plane's rectangle. A rectangle as an argument is **refused**: a
destination window somewhere else in the ring would need the plane to crop at `SRC_X/SRC_Y`, and it crops
from the ring's first byte and no other. Sizes are rounded down to a whole AFBD block of columns and an
even line count, because rounding up would show a strip of the previous frame. Like `aspect` the windows
are read at the next publication, so a change on a live plane costs the same half second of console while
the plane goes down and up. `ctl save` keeps the verb (`zoom = in 2.00`) and the next start applies it; a saved `out N`
from an older image reads as `off`. It
before the first picture; the full-panel rectangle older versions saved is read as `off`.

Two honest caveats. The firmware re-runs its window chain when we republish the record - it did, at once,
in the runs above - but it has been seen not to move for some geometries; if the wall does not follow, the
window was asked for and refused, not set and lost. And the scaler's own register `0x05180034` shows what
the firmware last did, not what was last asked, and can lag by a change. Judge a zoom on the wall.

### The warp: a third picture state beside plane and console

Since 22.09.2026 the keystone can draw the picture instead of the video plane:
[`h713-warp`](h713-warp.md) renders the capture through the GPU and this program commits the result on the
**video** plane with the daemon's fence (NV12, `hdmi-ring` 0; until 23.09.2026 it was RGB on the primary
plane, which the firmware's picture controls never reached), the console untouched. `ctl status` then reads
`picture warped (h713-warp draws on the video plane)`, and `ctl warp status` answers
`ok warp on -- h713-warp draws, video plane N, 1920x1080 NV12, line pitch P, C commits, B busy, E refused` - or
`ok warp off -- nothing claimed` when the daemon has not taken the panel. While the warp is on, `ctl zoom` is
refused with `the warp is on - use h713-warp ctl zoom`, because a zoom is the display firmware scaling into the
capture ring and the ring is not what the panel shows then; `ctl off` releases the warp and brings the console
back. A warp frame that arrives more than 25 ms after the previous one, or a commit that takes more than 10 ms,
is counted, not logged one by one: at most every 10 s one line says how many and the worst of each (`timing in 10
s: 247 warp frames more than 25 ms after the previous one (worst 66.9 ms), 0 commits over 10 ms`). Until
11.10.2026 it was a line per frame - 27 a second for a source with 30 distinct frames, 1.5 % of a core in journald.
The audio follows a warped picture like any other: "there is a picture" means the plane is on **or** the
warp draws. Until 22.09.2026 it meant the plane alone, so a source that changed its sample rate during a warp
was read as *no picture* and muted itself.

### The first picture: one switch, straight to the warped picture

Since 17.10.2026 `h713-warp` keeps a second connection to the control socket open, the *want link*, and says on it whether
it will claim the ring when this program lets it: `warp want ring` (a keystone, a mirrored mount, a test pattern) or `warp
want none` (the identity, `warp = off`, a ring geometry the GPU refused, a GPU that failed the last claim until a frame is
drawn again; said before the warp gives a claim back). With `ring` this program does not put the straight capture ring on
the video plane once the signal stands - at the start, when the signal comes back, after `ctl auto`, after the warp's
release or restart: it says `note claim` on the want link, the warp claims at once instead of at its next try once a
second, and this program waits for that claim at most one second. The claim finds the video plane off and leaves it off;
the warp's first frame turns it on, directly with NV12. The wall goes from black (the console, or a page) to the warped
picture in one switch. Until then the straight ring stood on the whole panel for 0.12 to 1.2 s (under the start launcher it
showed outside the keystone quad), the claim switched the plane off and the warp's first frame on again, and at that
switch from the NV16 ring to NV12 the box's camera saw one frame with false colours at every claim (HY310, 17.10.2026,
12 of 12; Marco saw it green). Without a claim within the second the straight ring comes after all, with the journal line
`h713-warp did not claim within ... -- the straight ring after all`, and stays until a claim's first frame; a ring claim
this program cannot take (no plane, no buffers, no master) ends the wait at once. A want link that closes while it says
`ring` keeps that word for one second (a restart of h713-warp), and a new link with `ring` starts the wait anew. Without a
want link - no h713-warp, or one of before 17.10.2026 - and with `none` the ring comes at once, as before: the HY300PRO-G-EU,
whose warp stays in bypass, is meant to see no wait (not measured there). Under an opaque page nothing waits, but the
signal is measured and h713-warp hears `note claim` all the same: its claim pauses under the page at once, and its first
frame after the page carries the page's end. `ctl status` says it on the `want` line; the journal says when the ring waits
(`the straight ring waits for h713-warp's claim`), the claim after how many milliseconds of waiting, and when its first
frame turned the plane on (`first frame: the video plane on ..., N ms after the claim`). Measured on the HY310 on 17.10.2026
(1080p60 source, the box's camera at 25 frames a second): `ctl off`/`ctl auto` 8 of 8 without a straight or a tinted frame,
the warped picture 0.28-0.31 s after `ctl auto` (the journal: the first frame 0.14 s after it; before, 1.35 s with 1.1 s of
the straight ring); the source's DPMS off and on 3 of 3, the picture 0.20-0.22 s after the signal; a restart of h713-warp
3 of 3, at most 0.52 s without a picture; two warm starts with the start launcher: no straight ring in the journal, the
warp claimed under the page 15-75 ms after the signal, and the page went to the warped picture (camera: no straight, no
tinted frame); a standby: the same in the journal. The service switch `h713-warp ctl off`/`on` keeps its straight ring
while the warp is off, as it should, and at `on` the plane still goes from the NV16 ring through off to NV12, with one
tinted frame at that switch (5 of 5). Not measured on the HY300PRO-G-EU.

### Under an opaque page: the mode pauses, picture and sound

An overlay that h713-osd shows with `osd show N cover` is an opaque page (the launcher, a settings page): once it is on
the wall it hides the whole picture, and the mode under it pauses (17.10.2026, measured on the HY310: see h713-warp, "Under an
opaque page"; the sound part was not measurable there - the source sent no sound). h713-warp
hears `note cover on` on its claim's connection and draws nothing more, and the video plane goes **off** under the page
(17.10.2026 evening: nothing of HDMI behind a page; a frame the warp sent before it heard the page is answered and not shown) -
the claim, the capture, the link and HDCP stay. The warp's first frame after the page turns the plane on again. Without a warp
claim the straight ring goes off under the page the same way and comes back after it. `capture` in the journal says when the
HDMI capture stops being needed (a page, a program as the mode) and when it is needed again - the place for a firmware switch of
the capture (not built). The HDMI sound goes quiet with the picture behind the automaton's own mute alone - the input mute where the DSP mixes
the box's own sounds, the DSP mute otherwise - with route, rate, switch and the DAC's source untouched: no click, and it
comes back with the picture without the debounce. When the page goes, or turns into an overlay over the picture (the
settings' slider pill, `osd show N` without `cover`), h713-warp hears `note cover off` and draws at once; the change of
the primary plane waits for that frame (at most 100 ms, then it goes on its own), so the wall goes from the page to a new
picture in one commit. A page shown while the warp waits for nothing goes on its own (the launcher's next row). The late-
frame count of the warp does not count the pause. `ctl status` says `cover`; the `audio` line says "muted under an opaque
page". Over the straight ring (no warp) only the sound pauses - the firmware draws the ring, there is nothing of ours to stop.

For example, `h713-tv ctl preset cinema` switches picture mode and its nine controls in one call. Startup
mode and remembered deviations live in `/etc/h713/tv.conf` (`start = auto|manual|last`, `state`, `preset`,
`data`, `calculator`, `edid = block0|block1`, `edid_prefer = file|panel`, `source = hdmi|client|auto` - the older words `manuell` and `zuletzt` and the older German key names `zustand`,
`daten`, `rechner` are still accepted) and `/var/lib/h713-tv/`; the values themselves come from `h713-pq`,
run once as a child process at startup.

### No signal as a page, not the console

In the mode HDMI with nothing to show - no signal (a source that is off, a cable out, a source that sends nothing for a moment), a source the
display firmware's table does not carry, a ring the plane does not take - the wall shows h713-osd's opaque page **No signal on HDMI / HOME: menu**
([h713-osd](h713-osd.md), "The page without a signal"), not the Linux console: the wall shows nothing that nobody ordered. The console is for
`h713-tv ctl off` (the service: it holds until `ctl auto`), for a program as the mode, where the signal does not matter, and for an image without
h713-osd.

h713-tv tells h713-osd on the overlay connection, unasked: `note signal none` while the page is wanted, `note signal TEXT` when it is not (the
signal's name; `off` for a forced console and for a program), and answers `osd signal` with the same word (asked once after each claim).
`ctl status` has a line `nosignal`: `none`, `waiting for the page`, `page: h713-osd shows "No signal on HDMI"`, or `no page: ...` with the reason.
`status brief` carries it too; h713-settings reads `nosignal        page` for its sentence "On the wall now: No HDMI signal".

**The wall in between.** When the signal goes, the picture on the wall stays - the ring, or the warp's last frame, frozen - until the page is on
the wall, at most one second, and the page then covers it; the warp's claim is released under the page. Before, the claim went at once and the
console showed for the tenth of a second h713-osd needs to draw the page through the keystone. The daemon h713-warp releases its claim on its own
as well, a tenth of a second after this program saw the signal go (its own QUERY_DV_TIMINGS says "Link has been severed"): while the loss is decided
and the page is wanted but not on the wall, that release leaves the claim standing without its connection (`h713-warp let go -- its claim and the last
frame stay until the page is up`), the page is committed on its own, and the claim goes under it. A page that does not come within the second
(h713-osd not running, or hung) gives the console after all, with a journal line; a signal that returns while such a claim stands releases it first.
A signal that is "changing" (the geometry has not locked yet) is not a loss: no page, no wait, as before.

**The way back.** When the signal stands again and h713-warp is to claim the ring, the page stays until the claim is made - it pauses under the
page, and its first frame carries the page's end, one commit from the page to the warped picture, no straight ring in between (the first picture,
above) - at most one second (`WARP_HOLD_MS`), then the page goes without it. Without a warp (identity, `warp = off`) the page goes with the word and
the straight ring follows after it.

Measured on the HY310 on 17.10.2026 (a laptop as the source, switched off and on with `xset dpms force`, a bright still page on it; the box's camera at 313
exposure and the journal): after every loss the page stood (the camera classified 182 of 182 frames in the window as the page, none as the console, in two
cycles with the lingering claim below and three more before it), a console forced with `ctl off` without a signal showed the console (101 of 101 frames), `ctl
auto` the page again (80 of 80). From the journal line `signal ...` to the first new address on the video plane (AFBD +0x70) after a return took 0.035, 0.101 and
0.101 s (3 of 3), the camera's first whole picture 0.22 to 0.24 s after it, with no straight ring and no tinted frame; the claim was made under the page 12 to
78 ms after the signal line and its first frame 13 to 15 ms after the claim, in one commit with the page's end. On the way to the page the journal has no
`console back with the warp's release` (without the lingering claim it had, with the page 150 ms later). After a standby from the state without a signal the page was
back on the wall about 9 s after the wake - the kernel console shows meanwhile, because h713-tv restarts and h713-osd claims again only when it listens - and stood
(camera: the same page as before the sleep, structure 14.7 against 14.6; the laptop switches its output on again when the link drops, so it was held off every
second for that test). Not measured on the HY300PRO-G-EU (720p panel, the warp in bypass: the page there is drawn straight when `warp = off`, and `want none`
means no wait for a claim).

## The EDID without Deep Colour

The display firmware does not take 10 or 12 bit per channel, and the vendor's EDID offers it (`DC_36bit`, `DC_30bit` and `DC_Y444` in the HDMI vendor block). A source that renegotiated to 12 bit after the port was restarted (a replug, a standby, the return from a parked capture) sent 1080p60 at a 222.8 MHz pixel clock, which the firmware's table has no record for, and the wall showed the console instead of a picture: a laptop with HDCP 1.4 on, 2 of 2 measured on 17.10.2026. So every EDID `h713-tv` publishes loses its Deep Colour bits, in the place where it already drops the modes the table lacks: `DC_48bit`, `DC_36bit`, `DC_30bit` and `DC_Y444` of the HDMI vendor block (OUI 00-0C-03), `DC_30bit_420`, `DC_36bit_420` and `DC_48bit_420` of the HDMI Forum block (OUI C4-5D-D8, if a file has one; the vendor's has none), with the extension's checksum computed again. Supports_AI, the maximum TMDS clock, the SCDC flags, every mode and every other vendor block (Dolby Vision) stay, and `/lib/firmware/hy310-edid.bin` itself is not touched.

It goes out by `ctl edid block0|block1`, by the plain `replug` (the read-back, the copy or the file, both EDIDs of the four blocks) and at start. At start a served EDID that still offers Deep Colour, which is what the firmware serves after every boot, is published again once without it, with one journal line naming the bits (`offers deep colour (DC_Y444 DC_30bit DC_36bit) -- published again without it`), also with `edid =` in `tv.conf`; a restart of the program finds it clean and does nothing. `ctl status` says `no deep colour offered` or names the bits that are still on.

Measured on the HY310 (17.10.2026): the EDID read back from the firmware (`VIDIOC_G_EDID`) had the flags byte 0xb8 before and 0x80 after, byte for byte the vendor's half without the three interlace VICs and without the Deep Colour bits, and the laptop's own copy of it (`xrandr --verbose`) showed the same change. With HDCP 1.4 requested on the laptop, the port restart through `SetSource` 1 and 3 ended in 222.8 MHz and the console with the old program (1 of 1 here, 2 of 2 earlier) and in 1080p60 at 148.5 MHz with a picture 3 of 3 with the new one; a replug did the same (3 of 3), and after a warm start the first lock behind the boot's republish was 148.5 MHz. Not measured: a source that takes Deep Colour from the Dolby Vision block of the 2.0 half, and the HY300PRO-G-EU.

## White balance and colour management

**On the HY310 the colour management has no visible effect** (20.10.2026, measured with the camera in fourteen states: the registers `0x05140300..440` are written and read back, the picture does not change; the chroma gain of the same block works, and in the blocks the vendor's register dumps hold no enable, clock or routing bit of the video path differs from the vendor's; the HY350 under the vendor's system carries the colour manager block byte for byte the same). The settings page and the panel no longer offer it; `ctl set cm_*` stays. The white balance works. *Before 20.10.2026 this page took the colour management for working on the strength of an eye test that was not a measurement.*

The display firmware has two picture settings that are neither V4L2 controls nor part of the gamma curve: the white balance (gain and offset per colour, the registers `0x051C00D4`..`0x051C00E0`) and the colour management (hue, saturation and value per colour axis, `0x0514030C`..`0x05140430`). The vendor's factory menu sets them with two calls into the firmware, `THal_Vp_SetWhiteBalance` (`0xfc42fe0c`) and `THal_Vp_SetColorManagement` (`0xf00ca77d`), and so does `h713-tv`: it writes a block of numbers into the shared `cpu_comm` memory and calls the routine with the block's address, through `/dev/cpu_comm` (`ctl rpc` cannot do that: the release image has no debugfs, and the firmware takes the number as a pointer).

| Value | Range | Meaning |
|---|---|---|
| `wb_r_gain`, `wb_g_gain`, `wb_b_gain` | 0..1023, 512 neutral | the firmware's own scale: 512 is 1.0, 1023 about 2.0; `4 x value` up to 512 in the 12-bit register field (`wb_g_gain 563` gives `0x8cc`) |
| `wb_r_offset`, `wb_g_offset`, `wb_b_offset` | 0..1023, 512 neutral | 512 is 0, 0 is -2048 in the register field |
| `cm_AXIS_hue`, `cm_AXIS_sat`, `cm_AXIS_value` | -255..255, 0 neutral | a step **on top of the value the picture mode itself puts into that entry**; AXIS is `red lips skintone yellow yellow_green green cyan blue blue_purple purple reserve0 reserve1` (the vendor's order, the number is the hardware axis) |

**All six white balance numbers are sent every time.** The firmware does not read `0xFFFF` as "leave this one": it wrote blue gain 0 and offsets of -512 for it (measured on the wall, 18.10.2026). The colour management block always carries all 12 axes.

**The colour management is a step, not a value.** The board's picture modes write 36 colour values of their own (the HY310's standard mode: yellow saturation 90, red hue 147, ...; cinema differs in 17 of them). The vendor's menu writes the number itself, which on such a board would turn "saturation +10" into "saturation 10". `h713-tv` reads the firmware's own value of every entry the first time it changes one and keeps it in `/run/h713-tv-state/cm-base` (gone with the boot), so 0 means "as the board comes" and `cm reset` gives each entry back, sign bit included. A picture mode (`ctl preset`, `ctl set mode`, the start) rewrites those values: the steps are taken off before the mode is sent and laid on again after, with the new mode's values as the base. The sign of an entry is a bit in `0x05140300`.. that the vendor's HAL sets directly; so does `h713-tv` (through `/dev/mem`), before the call.

**Where the blocks are.** The firmware reads the white balance block during the call and the colour management block later, in its application thread, which compares it with a cache of what it wrote and writes only the entries that differ: the block stays where it is, and a re-send first sends the mismatching entries one off, so that the cache does not hide a change. The slots are in the `cpu_comm` region the HDMI receiver's driver already maps (offsets from the region's base, 0x4E300000 on the H713 boards):

| Offset | Size | Used by |
|---|---|---|
| `+0x36000` | 912 B | the HDCP 2.2 key (hdmirx) |
| `+0x37000` | 0x48 | the `Wce_SetWindow` structures (hdmirx) |
| `+0x37100` | 24 B | the six backlight PWM words of `allwinner,backlight-pwm-info` (hdmirx 0168; the HY300PRO-G-EU's board file has the property) |
| **`+0x37200`** | 32 B | **white balance**: six values, a mark, the mark inverted |
| **`+0x37300`** | 160 B | **colour management**: 12 x 3 magnitudes, zeros, a mark, the mark inverted |
| `+0x400000` | 55296 B | the staging block of `THal_Vp_Init` (hdmirx) |

Before a slot is written it must be all zero or carry this program's mark, else nothing is written and the answer names the words found. The region must be the one the board file names (`reserved-memory/cpu-comm@...`) and carry the transport's magic, and four strings of the firmware (the two RPC names, `wb_r_gain`, `OnHalColorManagementChange`) must be at the addresses they have in the display firmware the numbers come from: with another firmware the whole feature says so (`ctl wb`: `[not available: ...]`) and sends nothing, and the settings page hides its rows. The slots lie behind the receiver's last user and inside the window it maps. The firmware's own allocator grows upwards from `+0x2D000` (word 47 is its start, word 45 its size) and could hand out the same pages one day, so before every write `h713-tv` reads it again and writes nothing once its break has reached the slot; the break moves in whole pages (the smallest grant is a page), so a break at the start of the slot's page counts as reached, because the next allocation would take that page. Measured on the HY310 (18.10.2026): one page given out since the boot, the break at `+0x33000`, three pages below the slots; the receiver's driver has used `+0x36000`..`+0x37100` since its first picture without a collision being seen, and makes the same test before it writes its three blocks since kernel `0326` ([cpu_comm](../subsystems/cpu-comm.md#the-shared-memory-and-the-firmwares-allocator)). Not measured: the break on the HY300PRO-G-EU.

**When it is applied.** At the start, if the registers do not hold what is wanted (a restart of this program leaves an old, unsaved setting standing otherwise, and a warm start or a standby resets the firmware); at every `ctl set` of one of the values; and again after a `ctl resync` and after a source change event, if, and only if, the registers have changed. Each re-send is a journal line (`colour          white balance sent after a resync: 2 of 6 registers were off`). The kept values (`ctl save`, lines `wb_*` and `cm_*` in `/var/lib/h713-tv/werte`) apply whatever preset starts: the white balance belongs to the device, not to the picture mode. A kept value out of range is dropped by itself with its line number, as the nine controls are.

Measured on the HY310 (18.10.2026, kernel with `0321`, display firmware as in the image): every white balance value set and the registers read back from outside through `/dev/mem` (`wb_g_gain 563` `0x8cc`, `wb 480 492 ...` `0x780 0x7b0`, offset 496 `0xfc0`, 1023 `0xfff`); colour management on the axes red, yellow, cyan and purple with positive and negative steps (the sign bits read back), `cm reset` gives all 36 registers and the three flag words back byte for byte; a call takes 11-21 ms through `ctl` (a repair with two calls about 30 ms). A picture mode rewrites the colour management (standard to cinema: 17 of 36 entries); after the base moves with the mode, `cm reset` gives each mode its own values and a step is exactly that step on top (yellow hue 4 + 60 = 64 in cinema). `ctl resync`, `ctl off`/`auto`, `ctl replug` and `ctl edid block0` did **not** change the registers. After `save`, a deliberate `forget` of the registers behind the program and a restart, the start brings the kept values back (3 of 6 and 2 of 36 off in the journal); a warm start and an RTC standby with values kept: the registers equal those before (the start of `h713-tv` sets them). The settings page, with its keys fed through a FIFO, sets the same registers. Not measured: the wall (the picture's colour; the white balance and the yellow hue were seen on the wall in a first test with a probe program, not with this code), a camera, picture modes other than standard and cinema, the HY300PRO-G-EU (its firmware may carry other addresses; then the rows are hidden), HDCP sources.

## Gamma and colour temperature

Two settings of the panel's curve, in the display firmware's own terms:

| Control | Values | Default | Meaning |
|---|---|---|---|
| `gamma` | `0`..`4`, or the exponent as text `1.8` `2.0` `2.1` `2.2` `2.4` | `3` (2.2) | the gamma level: the exponent `level / 2.2` laid on the raw curve, so level 3 is the raw curve itself. A plain number is a level (`2` is 2.1, not 2.0); a number with a decimal point is the exponent; anything else is refused with the list |
| `colour_temperature` | `auto`, `normal`, `cool`, `warm` (`standard` is `normal`; `0`..`3` is the place in that list) | `auto` | which of the board's measured curves. `auto` takes the one the picture mode asks for, as the vendor's table does: cinema and hdr warm, vivid cool, the others normal (from the device's data; the compiled-in table says the same by name) |

`ctl get gamma` answers `ok gamma = 3 (2.2)`, `ctl get colour_temperature` `ok colour_temperature = auto (normal)`;
`list` and `status` show both. A picture mode (`ctl preset`, `ctl set mode`, the start) moves the curve only while
`colour_temperature` is `auto`; the level is the user's and no picture mode touches it. A board whose TSE lacks cool or
warm gets the normal curve instead, with a journal line and in the answer (`warm (normal: this board has no warm curve)`).
`save` keeps both in `werte` (`gamma = 3`, `colour_temperature = auto`); the start applies them. A level above 4 is
refused: the vendor's library does not check it and would black the picture.

**What is computed.** The vendor's library keeps the board's nine raw curves (3 channels x 1024 samples of 12 bit per
colour temperature; the TSE has three of them). A level is the exponent `(F / 100) / 2.2` with `F` = 180, 200, 210, 220,
240 for level 0..4. For the first curve after a start it takes the power law over all 1024 samples, and then it sends
the factory menu's 33 points (all 0 here) - at every start and every resume. From then on **every** curve is a cubic Bezier
fit through twelve knots (x = 0 51 102 204 306 409 511 613 716 818 920 1023) of the power law: each knot is
`trunc(pow(raw / end, g) * end)` per channel with its own end point `end`, plus its point (-50..+50), clamped to
0..4095, and the samples in between come from piecewise cubic Bezier segments with the Catmull-Rom tangents cut to half
the segment, a Newton solver for `t`, and a cut toward zero. `h713-tv` computes that form, because that is what the
vendor's system shows after every start (and what a user of the vendor's menu sees): at level 3 it is up to 5 of 4095
away from the plain raw curve (the end point 4091 instead of 4092), at level 0 up to 31 in the dark. The 33 points are
inside the computation but not offered (all 0).

Every operation rounds on its own, as in the vendor's code: `gamma.c` is built with `-ffp-contract=off` (a fused
multiply-add on arm64 moves a sample by one now and then), and `gamma_arith_ok()` checks the build at run time and
refuses the control if it was fused. `pow()` comes from the board's libm, not the vendor's; the sample nearest to a cut
over all states and levels of the HY310 and HY300 Pro curves is 4e-5 and 7e-6 from a whole number, seven orders of
magnitude over the error of `pow()`, so no other libm can move a sample there.

**How it reaches the CRTC.** A new blob and one atomic commit that carries only `GAMMA_LUT`, while a picture stands as well
as without one (the master is taken for the commit if nobody here holds it); the old blob is released afterwards. The
kernel writes the banks when the blob changes (kernel `0095`). A change takes 27-47 ms as `ctl` sees it (the journal line of the
program itself says 16-33 ms; the kernel waits up to 40 ms for the frame counter before it writes); the curve is also carried by every later `show`. A standby restarts the program, which
brings the saved level and colour temperature back at its start ([below](#after-a-standby)).

**How it was checked.** `tests/test_gamma.c` compares the arithmetic with the checksums of an independent description of
the library (written in Python, itself checked against the library's own code in an emulator): 15 + 15 curves of an
invented board, 5 with points, the solver root by root in all its branches and the Bezier form over made-up knot values
that smooth curves never reach. Outside the repository the same C code was compared with that description over every level and every state of the curves in
the TSE files of 15 boards (the HY310 and the HY300 Pro among them), each in the form after a start, by the power law and with
28 sets of points: 12,150 curves, every 6144-byte result equal. The published vectors of a second, independent description of
the library matched as well.

Measured on the HY310 (19.10.2026, display firmware as in the image, a picture standing - the ring through the warp, then Kodi): the CRTC's `GAMMA_LUT` read back through DRM (the blob the kernel holds, turned back into 12 bit samples) equals the
independent description byte for byte, 6144 bytes each, in all 38 readings: the curve before the change (the plain power law
the earlier version put there, so the description and the earlier version agree as well), the first curve after the start, all
15 combinations of level 0..4 and normal/cool/warm, every `ctl preset` and `ctl set mode` with `colour_temperature auto`
(normal for standard, game, computer and energy_saving, warm for cinema and hdr, cool for vivid; a fixed `cool` stays cool
over cinema, and `auto` again takes cinema's warm), `set gamma 4` while Kodi draws under cage and the curve after Kodi has
ended, and the saved level 2.0 with warm after a warm start and after an RTC standby (`save`, then the program starts anew).
A change takes 27-47 ms through `ctl` (10-15 ms where nothing changes), the first curve after a start 33 ms; the kernel
logged no `frame counter stuck` warning, and bit 28 of the control word `0x051C00E8` turns over with every real write. The
board's TSE is the one of the host (same SHA-256). The three banks themselves could not be read back: through `/dev/mem`
they are write ports and answer with one value per read that changes from read to read, never the data.

Not measured: the wall (the picture's brightness and colour; no camera), a frame doubled or dropped by a change while a
picture stands, HDCP sources, the HY300PRO-G-EU (its TSE has the same three states with other end points per channel; the
comparison with the description over its curves is done on the host, not on the board).

## After a standby

On an image built with [standby](../subsystems/standby.md) the display firmware does not survive the sleep: it is parked, the wall keeps the last picture, and `h713-tv` shows nothing new until `h713-power` has run `h713-mips-restart`. That script stops `h713-warp` and `h713-tv@*`, restarts the firmware, binds the HDMI receiver again with the HDCP 2.2 key ([hdcp](../subsystems/hdcp.md)), waits up to 60 s for the receiver's video node, finds it **by name** - the number can differ from before - and starts `h713-tv@<node>` and `h713-warp`, after resetting their start limits so that standbys in quick succession do not run into them. It refuses, with exit 2 and the firmware untouched, while another process holds the capture node open: an unbind would free memory that process still uses.

`h713-tv` is therefore a new process after every standby and starts as after a boot: `tv.conf` and the saved values in `/var/lib/h713-tv/` apply, and a control set by `ctl set` but never saved should be gone (follows from the restart; not measured after a standby). Measured for the saved gamma level and colour temperature (19.10.2026, HY310): after an RTC standby the program started anew with the saved 2.0 and warm, and the curve on the CRTC was the one of before the standby, byte for byte.

Measured on the HY310 (`doku/172`, `doku/174`, `doku/177`): the firmware is ready about 300 ms after its start and the picture path is back 3.9 - 5.3 s after the wake. From the wake to a picture on the wall with a laptop as the source took about 11 s: the firmware restart 4.5 s, then `h713-tv` pulls the hot-plug pin low for 300 ms at its start and the laptop needs a good 4 s to send again. With an unchanged EDID that replug could be saved (TODO 9.0, after the release).

The sound follows the picture. The audio DSP loses its power in the sleep and msp reads `error`; a sound from the box is refused rather than hanging, and a laptop's HDMI sound stayed away until the DSP was rebuilt. After the picture path is back `h713-mips-restart` rebuilds it through msp's `reset` file, up to three attempts; the journal says `audio DSP rebuilt (attempt 1)`, and the laptop's sound was audible again without a reboot (09.10.2026, `doku/174`). A DSP that stays down is a warning: no HDMI sound until a reboot. Not measured: HDCP 2.2 from a source after the restart.

## Limits

Only HDMI-1 is wired up; other firmware inputs are not. A zoom is a request to the display firmware, not a
scaler we drive: it takes effect at the next publication and the firmware decides whether to follow. Geometry tops out at the panel size, and what the
firmware locks onto (CEA and the common VESA modes at 60 Hz) is its table, not this program's - 120 Hz
variants and 1600x900 fall back to the console, named: `status` and the journal say
`1600x900p60, 108.0 MHz not in the firmware's table -- console`, so a source that is refused can be
told from one that is not there (kernel `0136m`, `0136v`, `0136w`). `rpc` is raw and blocks for the call's duration. A resolution
change costs about a second of console, which is the source's own signal loss during the mode switch.
