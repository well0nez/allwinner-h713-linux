# Known issues

This is what still gets in your way, and what to do about it. "open" means nobody has fixed it yet;
"by design" means it will not change because something else depends on the current behaviour; "fixed in
git, not in the image" means the source has the fix but the image you can currently install does not yet.

## Not built, or not proven yet

| Issue | Why | Workaround |
|---|---|---|
| No Bluetooth | The driver builds, but the AIC8800D80's Bluetooth firmware (`fmacfwbt_*`) is not in the stock firmware - only in a separate SDK package with an unresolved licence. Wi-Fi is unaffected; it ships its own firmware set. | none |
| No AV1 decode | The H713 is the first Allwinner chip with AV1 hardware, and it is not yet clear whether the existing reverse-engineering covers a working driver or only the register layout. | none |
| No HDCP 1.4 | Confirmed on this chip: HDCP 1.4 keys live in hardware, decrypted by the Crypto Engine straight into a key sink (`0x03041400`) that DRAM never sees. A Linux driver would have to program that engine with key-select 3 (RSSK) before the MIPS starts - untested whether the non-secure world is allowed to do that at all. That test costs a power cycle and is deferred past the first release. | Use an unprotected source, or one that only needs HDCP 2.2 |
| HDCP 2.2 - one proof outstanding | Works: the 912-byte key is pulled from your device's own secure storage at boot and handed to the display firmware (verified 2026-09-11, key load at 6.4 s, driver sequence complete at 6.5 s). What is **unverified** is whether those 912 bytes are plaintext or a TEE-side ciphertext - that needs an actual HDCP-mandatory source (streaming stick, console, Blu-ray player) on the HDMI input to observe. | none needed unless the source refuses to negotiate |
| Hardware video decode, IOMMU | Unverified **in this image** - these come from cstenger's tree and are proven working there, not re-tested here. (The Mali GPU came the same way and is measured here since 22.09.2026: it carries the keystone.) That tree also has an open memory-corruption case under `mpv` (KASAN work in progress) - unverified, not reproduced by us. | none |
| EDID modes incomplete | The 512-byte EDID blocks go to the display firmware unchanged; which modes that unlocks is not worked through. 1600×900 is explained rather than fixed: the firmware's own mode table carries no record for it, so the driver refuses it by name. Block 1 of the HY310's EDID does offer 1080p100/120 and can be published through the ARISC's block mask, but no such source has been run here. | Use a mode the firmware's table carries; the driver names one it does not |
| Autofocus convergence against a wall is open | [`h713-autofocus`](tools/h713-autofocus.md) runs the vendor's search on the device, takes the panel over for its chessboard and gives it back. A latched edge only decides the starting direction, and the search turns round at one: on 24.09.2026 bench runs found a peak (positions -2 to +31, 440 msteps from the lower edge). What is unproven is a run against a wall at one to three metres. | Point it at a wall and report the last line (`stopped: peak` is the good one); focus by hand meanwhile ([guide](guides/autofocus.md)) |
| The firmware's zoom is the magnifier only | `h713-tv ctl zoom in/off` was measured with a test pattern on 22.09.2026 and enlarges the centre. `out` is gone (24.09.): the DE scaler only enlarges, so a smaller destination window cropped instead of shrinking, measured at 0x05180008. The projection area is `h713-warp ctl zoom`, which shrinks the picture inside the keystone matrix as the vendor does. | Use the zoom on the settings page |
| The keystone is two days old | [`h713-warp`](tools/h713-warp.md) and [`h713-keystone`](tools/h713-keystone.md) were built and measured on the HY310 on 22. to 24.09.2026 - a corner set by hand moves that corner on the wall, the automatic answers a nose-up tilt by pulling the top edge in, the tearing self-check passes, `v0.95-beta` carries them - but the hour-long soak has no result yet, and the throw ratio the automatic computes with is the optics' own 0.8176 out of `camprjspe.ini`, not a measured number: if the real one is nearer 1.2, every automatic correction is too strong. The vendor's edge-blend pass and the projection-mode mirror RPC are not built at all, and the write-back self-test that would prove the identity warp pixel-exact needs a debug kernel and was left optional. | Set the corners by hand; `h713-warp ctl keystone reset` and `ctl off` are the way back to the plain picture at any time |
| A frame that arrives while the previous commit is in flight is dropped | `h713-tv` commits the warped frame non-blocking and answers `ok busy` when the previous commit has not flipped yet; the warp then draws the same buffer again instead of queueing. The first run of 22.09. lost 8 to 11 of 1,030 frames; the minute-long A/B of 24.09. lost none. The render adds no latency of its own, but the warp holds each slot one vsync before drawing it - one frame, 16.8 ms - because the firmware publishes a slot before it has finished writing it ([keystone guide](guides/keystone.md)). | Nothing to do; `h713-warp ctl status` counts `busy` |
| Vertical lines on fast motion under the warp | Fixed 24.09.2026, in `v0.95-beta`. The firmware hands a ring slot on before its last lines are written (the bottom line still changed 11.5 ms after the publish), so the GPU mixed two frames. The warp draws a slot one vsync late; `h713-warp ctl check 900` proves it on any device: 900 frames, 0 differing rows; on the installed `v0.95-beta` twice 300 frames, 0 differing. The check itself drops frames while it runs (about every second one, skipped as stale) | Run the check after any change to the warp, `h713-tv` or the capture driver |
| The settings page has no authentication | Whoever reaches port 8080 can set the picture, move the focus motor and start the autofocus. The Wi-Fi password is the door; on a wired LAN there is none | Change the shipped Wi-Fi password; keep the projector off networks you do not own |
| The automatic keystone has to be shown what "level" is | `h713-keystone reference`, taken with the projector standing the way it is meant to throw, writes the pose that is corrected against into `/etc/h713/keystone-ref`; without it the automatic does not run. A pose more than 45 degrees off flat is refused (the vendor's own gate), and a reference taken under one axis map is refused under another, because its numbers describe a different pose. The sensor is not quiet either: one raw triple at rest spreads about 0.1 g, and even with thirty triples averaged the eight values still scatter by about half a degree, some 14 per-mille - which is why the loop applies a change only after it exceeds one degree and has stood for a second. | Take the reference again after every move. At rest the picture may still breathe by a fraction of a per cent |
| `backlight_level` and `dynamic_backlight` do nothing | The display firmware takes both controls and answers the call, and the lamp does not change - measured at 60 and at 10 on 22.09.2026. This is the same path [dead-ends.md](dead-ends.md) already records: on the HY310 neither PWM2/PB4 nor the two backlight calls move the lamp. The controls stay for a board that wires the rail up. | none - the lamp is not adjustable on this board |
| Swapping the `afbd` module at run time does not bring the new window | The display firmware does not take a republication after an `afbd` reload: it rebuilds only its capture, with its own standard window. Measured on the HY300 Pro over the bridge, 22.09.2026 - the four descriptor words became 30720x17280 as intended, the scaler window stayed at 852x478, and the driver reported that the firmware did not reprogram the chroma stride within 1000 ms. | Put the module in `/lib/modules` and reboot. The same module then comes up with the right window (720p and 1080p confirmed by the owner) |

| No picture after plugging a source in | Fixed 16.09.2026 (kernel patches 0136a, 0136c): the driver used to switch the firmware's source away and back after the first publication, and that switch kills any HDMI port that was not locked a moment ago - the firmware reported no signal until the cable was pulled and put back. The first publication now releases the capture directly, like every later one. Verified on the HY310: a source plugged in after boot, a boot with the source plugged in, `ctl auto` 30 s after boot, and an unplug and replug. | Nothing to do on an image from 16.09. on. On an older image, `h713-tv ctl replug` brings the picture. |

| The sound dropped out while the warp was drawing | Fixed 22.09.2026 in the source, not yet in any image: the audio automaton read "the video plane is on" as "there is a picture", and while `h713-warp` draws, that plane is off and the primary one carries the picture. A source event during a warp - a player changing its sample rate - was therefore re-evaluated as *no picture* and muted the path with a pop. All five places ask for "plane on **or** warped" now. Found on the HY310 during the first long warp run. | On an image without the fix, do not warp a source that changes its sample rate; there is no runtime switch for it. |

| Latency spikes on the access point | A client at −50 dBm, linked at 72 MBit/s, sees ping times jumping between 3 ms and 2 s while throughput is fine (5.7 MB/s measured 2026-09-12 over SSH). It looks like power saving on the radio rather than the link itself; not investigated. | Bulk transfers are unaffected. For interactive work over Wi-Fi, or if it bothers you, use the wired path or `mode=sta` on an existing network. |

## By design

| Behaviour | Reason |
|---|---|
| The warp and the ring are mutually exclusive on the video plane | While `h713-warp` draws, the video plane carries the GPU's NV12 frames with `hdmi-ring` 0 instead of the capture ring - so the display firmware's magnifier (`h713-tv ctl zoom in`), which scales the ring, has nothing to scale and is refused; the nine picture controls act on the warped frame, because it runs through the same channel |
| The GPU userspace is 15 MiB, and panfrost only | mesa is cross-built for this image instead of installed from Debian, where `libgbm1` alone pulls `mesa-libgallium` and `libllvm19` - 187 MiB installed, against a 258 MiB tree. Ours carries the panfrost driver, EGL, GLES2 and GBM and no LLVM, X11, Wayland or glvnd: 15 MiB under `/usr/local`, where a later `apt` mesa cannot collide with it. There is no Vulkan driver, no desktop stack and no second GPU driver in it, and `build-rootfs.sh --mesa none` leaves the whole thing out. |
| No desktop in the shipped image | The image runs `h713-tv`, a fixed HDMI-input service, not a compositor - the projector's job here is the HDMI input. The KMS device (`card1`) is a normal DRM device underneath; nothing stops you from running a compositor on it instead ([docs/subsystems/display.md](subsystems/display.md)). |
| No temperature reading | This unit has no NTC: both of the device's own decompiled device trees say `ntc_num = 0`, and the vendor code treats that as binding rather than fabricating a value (confirmed 2026-09-11, `doku/60` "Der NTC war ein Phantom", patch `0152`). Heat protection runs off the **tachometer** instead - a stalled fan powers the device off (patch `0159`), the same trigger the vendor firmware uses, and the one signal here that is verified (PB5 off → 0 RPM, on → 4770 RPM). A board variant that does carry an NTC picks it up automatically through `ntc_num`. A device that overheats with a *turning* fan is covered by nothing, so keep the vents clear. |
| The projector waits for the power key after being plugged in | Same as with the stock firmware, and deliberate: [docs/uboot/power-gate.md](uboot/power-gate.md). `fw_setenv h713_gate 0` makes it boot on power instead. |
| `brightness` moves the black level, not the picture | The control writes the picture path's black-level offset (register `0x05001234`, read back following the control on 22.09.2026). On bright content that is invisible, on dark content it shows. It is the vendor's own meaning for this field, and `h713-pq` documents which register each control owns. |
| A source the firmware's table does not carry takes about seven seconds to be named | The display firmware is slow to write its record for an unknown raster. Six seconds after plugging such a source in, `h713-tv` still says "change in flight"; at eight seconds it names the source and shows the console, with one journal line - on 22.09.2026 that read `1600x900p75, 108.0 MHz not in the firmware's table`, and the 75 was the rate computed over the active size because the refused timing carried no blanking. Nothing is lost, the answer is late; the blanking is filled in the source since that run, so the line should read p60, which no device has confirmed yet. |
| Setting the EDID block mask publishes nothing by itself | The mask (in-kernel `arisc_hdmi_edid_mask()`, device tree `allwinner,edid-version-mask`, debugfs `edid-version`) stores a byte in the ARISC firmware; the firmware applies it when it next uploads an EDID, at the last fragment. Measured twice on the device, with and without the race that patch `0091e` closes. The default mask 0 is what ships, so port 0 keeps block 0. To make a changed mask visible, trigger a full upload afterwards ([arisc.md](subsystems/arisc.md)). |

## Untested paths

| Path | State |
|---|---|
| Installer on Windows | Not tried for this release; the documentation says so explicitly. `sunxi-fel.exe` for Windows is planned after feedback from Linux users (decision 2026-09-12, `doku/116` §2). Since layout v4 (2026-09-16) `install` is Linux-only in any case: it mounts the image's own file systems to copy your device's files into them, and says so in one sentence. `identify`, `dump` and `extract` mount nothing. |
| The image's files are copied in through a mount | Layout v4 (2026-09-16, after issue #1): the installer no longer writes the proprietary files into placeholders of a measured size but mounts `hy310-boot` and `hy310-rootfs` and copies them in as ordinary files, so a firmware whose files are bigger than the HY310's fits. Covered by tests that mount a real ext4 and read every file back, including through this project's own ext4 reader, and **accepted on the HY310 on 16.09.2026**: reinstall without a dump, files copied in through the mount, cold start, camera, Wi-Fi, HDMI hot plug. An image built for the old layout is refused by this installer with one sentence, and a v4 image likewise by the installer of its own release; use the installer that ships with the image you have. |
| Wi-Fi station mode - two corners | Both modes are verified (2026-09-12): access point with a laptop, station against a real network. Still untried: whether Android accepts the access point's DNS behaviour (it answers only for the device's own name, `REFUSED` otherwise) without flagging "no internet", and how `dhclient` in station mode interacts with a second DHCP client on `eth0` (two default routes, metric not decided). |
| Bright-image camera test | The internal camera is confirmed working as a V4L2 device, and a grab succeeds in 3.4 s - but every capture so far was of a dark room with nothing projected on the wall. A bright, in-focus picture from the camera has not been produced yet (2026-09-12, `analyse/boot/abnahme-v08-20260912.txt`). |

## Feature gaps

| Missing | Detail |
|---|---|
| No audio mixing with HDMI | The internal DAC accepts only one source at a time, and a PC connected over HDMI holds that source open continuously - device sounds (UI, alerts) cannot currently be mixed in (`doku/102`). |
| Standby is one stage only | Standby draws 4 W with the front LED red; a deeper sleep (under 1 W, instant-on, using the ARISC co-processor and IR/CEC wake) is designed but not implemented (`doku/104`). |
| Autofocus is not finished | The tool exists since 22.09.2026 ([`h713-autofocus`](tools/h713-autofocus.md), the vendor's own search rebuilt) and is a separate tool rather than a mode of `h713-focus`, because it needs a test pattern to measure against - against an arbitrary dark scene the metric is nonsense. What is missing is the proof that it converges: see *Autofocus does not converge yet* above. |

## The image on your device may not match a fresh build

Everything built before 2026-09-12 20:00 - the development builds of that week, long before the beta
releases - carries a BL31 (TF-A firmware) from 2026-09-10 with debug assertions still compiled in
(49,260 bytes). The build script never rebuilt it because `make` considered the existing binary current;
a clean build produces the intended release BL31 at 45,164 bytes, four bytes of which are just the
embedded build time. `release/build-all.sh` now wipes the TF-A and U-Boot build directories first, so
this is fixed in the source, and the release BL31 has been on the device since 2026-09-15
(STATUS.md "Boot chain"; `doku/116` §4a P3.9). Only images built before 2026-09-12 still carry the old one.

Details: `doku/61-todo.md`, `doku/60-offen.md`.
