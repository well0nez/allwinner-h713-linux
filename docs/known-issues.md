# Known issues

This is what still gets in your way, and what to do about it. "open" means nobody has fixed it yet;
"by design" means it will not change because something else depends on the current behaviour; "fixed in
git, not in the image" means the source has the fix but the image you can currently install does not yet.

## Not built, or not proven yet

| Issue | Why | Workaround |
|---|---|---|
| With the keystone warp on, SD and PC modes (480p, 576p, 1366x768, 1280x1024, 1680x1050 ...) show without keystone | The capture ring's line pitch is the mode's width, and panfrost imports a linear dma-buf only with a pitch that is a multiple of 64, so h713-warp cannot read those rings and leaves the picture to h713-tv (bypass). Until 05.10.2026 it retried once a second and took the plane each time: the wall blinked, green on the first frame of each return. 1080p, 720p and the firmware-scaled 4K ring (1920 wide) are warped. | None needed for the picture; keystone for those modes is TODO 2.4f |
| A 720p source with the keystone warp on shows the picture doubled and squashed | The display firmware's composition block scales and reads for the signal it detected: a 720p ring is 1280 bytes a line. When h713-warp takes the video plane it hands over 1920x1080 buffers from memory, and nothing behind the plane is reprogrammed for them, so the block keeps reading 1920-byte lines with a 1280-byte stride (kernel 0107 said this was not yet measured on the wall; measured 05.10.2026 with a Fire TV stick at 720p60: the warp's own frame is correct, `h713-warp ctl dump`, the wall shows it doubled). 1080p sources are unaffected, and 720p without the warp is correct. | Set the source to 1080p, or `h713-warp ctl off` for a 720p source. Fix pending (TODO 2.4a) |
| Bluetooth after a warm reboot | The chip's first HCI command after `reboot` sometimes goes unanswered (2 of 5 warm reboots on the HY310, cause open); the kernel never retries. `h713-bt-reset` resets the controller on the bare UART before and after the attach and the unit restarts until `hci0` is UP - measured UP after about 10 s on three warm reboots in a row. A cold start never showed it on the HY310; on the HY300PRO-G-EU the first attach after a cold start still does not get through (04.10.2026: `hci0` not up after 10 s, then systemd restarts the unit and the second start brings it up, about 17 s later than on the HY310). | none needed; `journalctl -u h713-bluetooth` shows the tries |
| No AV1 decode | The H713 is the first Allwinner chip with AV1 hardware, and it is not yet clear whether the existing reverse-engineering covers a working driver or only the register layout. | none |
| No HDCP 1.4 | Fixed 05.10.2026. The refusal was real but it was not a wall: the engine declines key-select 3 towards readable memory **by design** (error 0x11 - that would be key export) and accepts it only when the destination is the receiver's key sink **and** the DMA source lies inside the protected window. Both refusals look identical from outside, which is what made this look hopeless for two days, and it is why the eFuse flag reading zero was a red herring - the flag was never what the engine went by. The maker's firmware authenticating on the same unit (04.10.2026) was the clue that mattered. The boot loader now stages the stored key set inside that window and our own EL3 service hands it to the sink; no unwrapping is needed, because the stored bytes are byte-identical to the source of the maker's own engine task. Proven at the picture with a cleared sink as the control, three pairs: `Desired` -> push -> `Enabled` ([`subsystems/hdcp.md`](subsystems/hdcp.md)) | Nothing to do on an image from 05.10. on |
| HDCP 2.2 - one proof outstanding | Works: the 912-byte key is pulled from your device's own secure storage at boot and handed to the display firmware (verified 2026-09-11, key load at 6.4 s, driver sequence complete at 6.5 s). What is **unverified** is whether those 912 bytes are plaintext or a TEE-side ciphertext - that needs an actual HDCP-mandatory source (streaming stick, console, Blu-ray player) on the HDMI input to observe. | none needed unless the source refuses to negotiate |
| The HY300 Pro of issue #1 has no green run yet | Its lamp dimmer is a PWM the display firmware owns; the vendor tells the firmware channel, polarity and frequency (`panel_config.ini` [PWMSetting]: 5, low active, 40 kHz) before the level, and `0166` sends them from the board file. `hy300-pro-test9` (25.09.2026) then stopped at random places: it sent the six words as six parameters where the firmware reads one address - the crash the HY300PRO-G-EU showed, fixed by kernel `0168` (03.10.2026) - and its U-Boot ran project 0x30 instead of 0x34. On the HY300PRO-G-EU the weak, washed-out picture was the LVDS at 6 bit; U-Boot drives project 0x34 at 8 bit since `2de0cc8`. `test10` carries all of it and follows after `v0.96-beta` ([boards/hy300-pro](../boards/hy300-pro/README.md)) | none needed on the HY310 (its dimmer on PB4 is not wired) |
| Hardware video decode, IOMMU | Unverified **in this image** - these come from cstenger's tree and are proven working there, not re-tested here. (The Mali GPU came the same way and is measured here since 22.09.2026: it carries the keystone.) That tree also has an open memory-corruption case under `mpv` (KASAN work in progress) - unverified, not reproduced by us. | none |
| Two modes the EDID offers do not lock, and 1080p100/120 are behind a switch | Worked through in working journal `FB-EDID` (`tables/edid-vs-firmware.csv`): every CEA mode block 0 offers has an enabled record in the firmware's table, but two of the base block's standard timings do not - 1600x1200@60 (its records exist and are disabled) and 640x360@85 (no record) - so a PC that picks them gets the console and the line `not in the firmware's table`. 1600x900 is in neither EDID half; a source that sends it chose it on its own, and the answer stays the same line. Block 1 adds 1080p100/120, which the table carries (records 13 and 15), 1080i50/60, and 4K50/60, which it has disabled; `edid = block1` in `tv.conf` (or `h713-tv ctl edid block1`) publishes it as the served EDID through `S_EDID`, without the ARISC's per-port mask. A laptop's 1080p120 locked with block 1 on 02.10.2026; under the keystone warp such a source draws only about 19 frames a second (the GPU is busy, frames are dropped), which is not explained yet | Pick a mode the EDID offers other than 1600x1200 or 640x360; for 1080p100/120 set `edid = block1`, and leave the warp at identity for 120 Hz |
| Autofocus: one evening at one wall | [`h713-autofocus`](tools/h713-autofocus.md) runs the vendor's search on the device, takes the panel over for its chessboard and gives it back, waits until the pattern is on the wall, and turns round at an edge. On 02.10.2026 two runs ended `stopped: peak`, though at counter positions far apart (-3 and +41), and a run against a wall ended sharp at the same motor position as the run before (`doku/134` A4). That is one evening and one wall; the metric's span was only +11 % that day (the camera's exposure is the suspect). | Point it at a wall at one to three metres and report the last line (`stopped: peak` is the good one); focus by hand meanwhile ([guide](guides/autofocus.md)) |
| The firmware's zoom is the magnifier only | `h713-tv ctl zoom in/off` was measured with a test pattern on 22.09.2026 and enlarges the centre. `out` is gone (23.09.): the DE scaler only enlarges, so a smaller destination window cropped instead of shrinking, measured at 0x05180008. The projection area is `h713-warp ctl zoom`, which shrinks the picture inside the keystone matrix as the vendor does. | Use the zoom on the settings page |
| A reinstall resets your settings and the remote's pairing | A reinstall over our own layout carries the vendor files, the board record, `h713_project` and the U-Boot keys `h713_gate` / `h713_boot` over, but writes a fresh root filesystem: the keystone corners, the zoom and the picture values in `/etc/h713` and `/var/lib/h713-tv` start from the defaults again, and the remote has to be paired again (its bond lives in `/var/lib/bluetooth`). Seen on both devices on 04.10.2026. | note your corners first (`h713-warp ctl status`); pair the remote with Left+Right after the first boot |
| The keystone has no long run behind it | [`h713-warp`](tools/h713-warp.md) and [`h713-keystone`](tools/h713-keystone.md) were built and measured on the HY310 from 22.09.2026 on - a corner set by hand moves that corner on the wall, the automatic answers a nose-up tilt by pulling the top edge in, the tearing self-check passes, and the projection modes and the soft edge were judged on the wall on 02.10.2026 - but the hour-long soak has no result yet, the ceiling modes were seen with the projector upright on the bench, not upside down, and the throw ratio the automatic computes with is the optics' own 0.8176 out of `camprjspe.ini`, not a measured number: if the real one is nearer 1.2, every automatic correction is too strong. The write-back self-test that would prove the identity warp pixel-exact needs a debug kernel and was left optional. | Set the corners by hand; `h713-warp ctl keystone reset` and `ctl off` are the way back to the plain picture at any time |
| A frame that arrives while the previous commit is in flight is dropped | `h713-tv` commits the warped frame non-blocking and answers `ok busy` when the previous commit has not flipped yet; the warp then draws the same buffer again instead of queueing. The first run of 22.09. lost 8 to 11 of 1,030 frames; the minute-long A/B of 23.09. lost none. The render adds no latency of its own, but the warp holds each slot one vsync before drawing it - one frame, 16.8 ms - because the firmware publishes a slot before it has finished writing it ([keystone guide](guides/keystone.md)). | Nothing to do; `h713-warp ctl status` counts `busy` |
| Vertical lines on fast motion under the warp | Fixed 23.09.2026, in `v0.95-beta`. The firmware hands a ring slot on before its last lines are written (the bottom line still changed 11.5 ms after the publish), so the GPU mixed two frames. The warp draws a slot one vsync late; `h713-warp ctl check 900` proves it on any device: 900 frames, 0 differing rows; on the installed `v0.95-beta` twice 300 frames, 0 differing. The check itself drops frames while it runs (about every second one, skipped as stale) | Run the check after any change to the warp, `h713-tv` or the capture driver |
| The settings page has no authentication | Whoever reaches port 8080 can set the picture, move the focus motor and start the autofocus. The Wi-Fi password is the door; on a wired LAN there is none | Change the shipped Wi-Fi password; keep the projector off networks you do not own |
| The automatic keystone corrects against an ideal level pose until it is shown a better one | Without `/etc/h713/keystone-ref` the automatic corrects against the ideal level pose (0, 0, 1 g) and says so on every result line (until 26.09.2026 it waited for the file instead). `h713-keystone reference`, taken with the projector on a surface a spirit level has passed, stores the pose the sensor reads there and prints its offset against the ideal - the sensor's mounting offset, which the stored pose then cancels. A pose more than 45 degrees off flat is refused (the vendor's own gate), and a reference taken under one axis map is refused under another, because its numbers describe a different pose - said once in the journal; the automatic corrects against the ideal meanwhile and the strip says `ref refused` until the reference is taken again. The sensor is not quiet either: one raw triple at rest spreads about 0.1 g, and even with thirty triples averaged the eight values still scatter by about half a degree, some 14 per-mille - which is why the loop applies a change only after it exceeds one degree and has stood for a second. | Take the reference once, on a level surface; the strip of the settings page says `ref ideal`, `ref set` or `ref refused`. At rest the picture may still breathe by a fraction of a per cent |
| `backlight_level` and `dynamic_backlight` do nothing | The display firmware takes both controls and answers the call, and the lamp does not change - measured at 60 and at 10 on 22.09.2026. This is the same path [dead-ends.md](dead-ends.md) already records: on the HY310 neither PWM2/PB4 nor the two backlight calls move the lamp. The controls stay for a board that wires the rail up. | none - the lamp is not adjustable on this board |
| Swapping the `afbd` module at run time does not bring the new window | The display firmware does not take a republication after an `afbd` reload: it rebuilds only its capture, with its own standard window. Measured on the HY300 Pro over the bridge, 22.09.2026 - the four descriptor words became 30720x17280 as intended, the scaler window stayed at 852x478, and the driver reported that the firmware did not reprogram the chroma stride within 1000 ms. | Put the module in `/lib/modules` and reboot. The same module then comes up with the right window (720p and 1080p confirmed by the owner) |

| No picture after plugging a source in | Fixed 16.09.2026 (kernel patches 0136a, 0136c): the driver used to switch the firmware's source away and back after the first publication, and that switch kills any HDMI port that was not locked a moment ago - the firmware reported no signal until the cable was pulled and put back. The first publication now releases the capture directly, like every later one. Verified on the HY310: a source plugged in after boot, a boot with the source plugged in, `ctl auto` 30 s after boot, and an unplug and replug. | Nothing to do on an image from 16.09. on. On an older image, `h713-tv ctl replug` brings the picture. |

| The sound dropped out while the warp was drawing | Fixed 22.09.2026, in `v0.95-beta`: the audio automaton read "the video plane is on" as "there is a picture", and while `h713-warp` draws, that plane is off and the primary one carries the picture. A source event during a warp - a player changing its sample rate - was therefore re-evaluated as *no picture* and muted the path with a pop. All five places ask for "plane on **or** warped" now. Found on the HY310 during the first long warp run. | On an image older than `v0.95-beta`, do not warp a source that changes its sample rate; there is no runtime switch for it. |


## By design

| Behaviour | Reason |
|---|---|
| The warp and the ring are mutually exclusive on the video plane | While `h713-warp` draws, the video plane carries the GPU's NV12 frames with `hdmi-ring` 0 instead of the capture ring - so the display firmware's magnifier (`h713-tv ctl zoom in`), which scales the ring, has nothing to scale and is refused; the nine picture controls act on the warped frame, because it runs through the same channel |
| The GPU userspace is 15 MiB, and panfrost only | mesa is cross-built for this image instead of installed from Debian, where `libgbm1` alone pulls `mesa-libgallium` and `libllvm19` - 187 MiB installed, against a 258 MiB tree. Ours carries the panfrost driver, EGL, GLES2 and GBM and no LLVM, X11, Wayland or glvnd: 15 MiB under `/usr/local`, where a later `apt` mesa cannot collide with it. There is no Vulkan driver, no desktop stack and no second GPU driver in it, and `build-rootfs.sh --mesa none` leaves the whole thing out. |
| No desktop in the shipped image | The image runs `h713-tv`, a fixed HDMI-input service, not a compositor - the projector's job here is the HDMI input. The KMS device (`card1`) is a normal DRM device underneath; nothing stops you from running a compositor on it instead ([docs/subsystems/display.md](subsystems/display.md)). |
| No temperature reading | This unit has no NTC: both of the device's own decompiled device trees say `ntc_num = 0`, and the vendor code treats that as binding rather than fabricating a value (confirmed 2026-09-11, `doku/60` "Der NTC war ein Phantom", patch `0152`). Heat protection runs off the **tachometer** instead - a stalled fan powers the device off (patch `0159`), the same trigger the vendor firmware uses, and the one signal here that is verified (PB5 off -> 0 RPM, on -> 4770 RPM). A board variant that does carry an NTC picks it up automatically through `ntc_num`. A device that overheats with a *turning* fan is covered by nothing, so keep the vents clear. |
| The projector waits for the power key after being plugged in | Same as with the stock firmware, and deliberate: [docs/uboot/power-gate.md](uboot/power-gate.md). `fw_setenv h713_gate 0` makes it boot on power instead. |
| `brightness` moves the black level, not the picture | The control writes the picture path's black-level offset (register `0x05001234`, read back following the control on 22.09.2026). On bright content that is invisible, on dark content it shows. It is the vendor's own meaning for this field, and `h713-pq` documents which register each control owns. |
| A source the firmware's table does not carry gets the console | The display firmware's mode table is the list of what locks. A raster outside it is refused and named from the firmware's own record (kernel `0171`), without the "change in flight" of older images: on 02.10.2026 a laptop's 1600x1200 read `1600x1200p60, 162.0 MHz not in the firmware's table`, with one journal line, and the picture came back within two seconds of switching to 1080p60. |
| Setting the EDID block mask publishes nothing by itself | The mask (in-kernel `arisc_hdmi_edid_mask()`, device tree `allwinner,edid-version-mask`, debugfs `edid-version`) stores a byte in the ARISC firmware; the firmware applies it when it next uploads an EDID, at the last fragment. Measured twice on the device, with and without the race that patch `0091e` closes. The default mask 0 is what ships, so port 0 keeps block 0. To make a changed mask visible, trigger a full upload afterwards ([arisc.md](subsystems/arisc.md)). |

## Untested paths

| Path | State |
|---|---|
| Installer on Windows | Not tried for this release; the documentation says so explicitly. `sunxi-fel.exe` for Windows is planned after feedback from Linux users (decision 2026-09-12, `doku/116` section 2). Since layout v4 (2026-09-16) `install` is Linux-only in any case: it mounts the image's own file systems to copy your device's files into them, and says so in one sentence. `identify`, `dump` and `extract` mount nothing. |
| The image's files are copied in through a mount | Layout v4 (2026-09-16, after issue #1): the installer no longer writes the proprietary files into placeholders of a measured size but mounts `hy310-boot` and `hy310-rootfs` and copies them in as ordinary files, so a firmware whose files are bigger than the HY310's fits. Covered by tests that mount a real ext4 and read every file back, including through this project's own ext4 reader, and **accepted on the HY310 on 16.09.2026**: reinstall without a dump, files copied in through the mount, cold start, camera, Wi-Fi, HDMI hot plug. An image built for the old layout is refused by this installer with one sentence, and a v4 image likewise by the installer of its own release; use the installer that ships with the image you have. |
| Wi-Fi station mode - two corners | Both modes are verified (2026-09-12): access point with a laptop, station against a real network. Still untried: whether Android accepts the access point's DNS behaviour (it answers only for the device's own name, `REFUSED` otherwise) without flagging "no internet", and how `dhclient` in station mode interacts with a second DHCP client on `eth0` (two default routes, metric not decided). |
| Bright-image camera test | The internal camera is confirmed working as a V4L2 device, and a grab succeeds in 3.4 s - but every capture so far was of a dark room with nothing projected on the wall. A bright, in-focus picture from the camera has not been produced yet (2026-09-12, `analyse/boot/abnahme-v08-20260912.txt`). |

## Feature gaps

| Missing | Detail |
|---|---|
| No sounds of its own | Since `v0.96-beta` the DSP mixes the box's own sounds into HDMI (`hw:hy310hdmi,0`, ALSA's default; [audio](subsystems/audio.md)), measured within 0.07 dB of the HDMI level. Nothing in the image plays one yet - no click on the settings page, no confirmation tone. |
| Standby is one stage only | Standby draws 4 W with the front LED red; a deeper sleep (under 1 W, instant-on, using the ARISC co-processor and IR/CEC wake) is designed (`doku/104`). A test build reached suspend on 03.10.2026 and never woke up, so it is parked and not in the image. |
| The remote's keys do nothing yet | The stock remote pairs over Bluetooth and its 16 keys and the mouse arrive as Linux input events (`docs/subsystems/wifi.md`), but nothing in the image maps them to the picture, the volume or the keystone. Power is the exception: logind shuts the system down on it. The IR receiver is parked - the mouse key and the microphone key send the same infrared code. |

## The image on your device may not match a fresh build

Everything built before 2026-09-12 20:00 - the development builds of that week, long before the beta
releases - carries a BL31 (TF-A firmware) from 2026-09-10 with debug assertions still compiled in
(49,260 bytes). The build script never rebuilt it because `make` considered the existing binary current;
a clean build produces the intended release BL31 at 45,164 bytes, four bytes of which are just the
embedded build time. `release/build-all.sh` now wipes the TF-A and U-Boot build directories first, so
this is fixed in the source, and the release BL31 has been on the device since 2026-09-15
(STATUS.md "Boot chain"; `doku/116` section 4a P3.9). Only images built before 2026-09-12 still carry the old one.

Details: `doku/61-todo.md`, `doku/60-offen.md`.
