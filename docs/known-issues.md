# Known issues

This is what still gets in your way, and what to do about it. "open" means nobody has fixed it yet;
"by design" means it will not change because something else depends on the current behaviour; "fixed in
git, not in the image" means the source has the fix but the image you can currently install does not yet.

| No HDCP 1.4 | Fixed 05.10.2026. The refusal was real but it was not a wall: the engine declines key-select 3 towards readable memory **by design** (error 0x11 - that would be key export) and accepts it only when the destination is the receiver's key sink **and** the DMA source lies inside the protected window. Both refusals look identical from outside, which is what made this look hopeless for two days, and it is why the eFuse flag reading zero was a red herring - the flag was never what the engine went by. The maker's firmware authenticating on the same unit (04.10.2026) was the clue that mattered. The boot loader now stages the stored key set inside that window and our own EL3 service hands it to the sink; no unwrapping is needed, because the stored bytes are byte-identical to the source of the maker's own engine task. Proven at the picture with a cleared sink as the control, three pairs: `Desired` -> push -> `Enabled` ([`subsystems/hdcp.md`](subsystems/hdcp.md)) | Nothing to do on an image from 05.10. on |

## By design

| Behaviour | Reason |
|---|---|
| The warp and the ring are mutually exclusive on the video plane | While `h713-warp` draws, the video plane carries the GPU's NV12 frames with `hdmi-ring` 0 instead of the capture ring - so the display firmware's magnifier (`h713-tv ctl zoom in`), which scales the ring, has nothing to scale and is refused; the nine picture controls act on the warped frame, because it runs through the same channel |
| The GPU userspace is 15 MiB, and panfrost only | mesa is cross-built for this image instead of installed from Debian, where `libgbm1` alone pulls `mesa-libgallium` and `libllvm19` - 187 MiB installed, against a 258 MiB tree. Ours carries the panfrost driver, EGL, GLES2 and GBM and no LLVM, X11, Wayland or glvnd: 15 MiB under `/usr/local`, where a later `apt` mesa cannot collide with it. There is no Vulkan driver, no desktop stack and no second GPU driver in it, and `build-rootfs.sh --mesa none` leaves the whole thing out. *Superseded 13.10.2026 on the `medien` branch:* the mesa is built with the Wayland platform and as a glvnd vendor (`libEGL_mesa.so.0`), so "no Wayland or glvnd" above no longer holds; `libEGL.so.1` and `libGLESv2.so.2` are Debian's glvnd dispatchers (`libegl1`, `libgles2`), which costs the base image 1.6 MiB (1.5 MiB of it `libGLdispatch`), and `libgbm1`, `libegl-mesa0`, `libgl1-mesa-dri`, `mesa-libgallium`, `libglx-mesa0` are dummy packages (`rootfs/equivs/`) that keep Debian's compositors and Kodi installable without LLVM. Still no Vulkan, no X11, no second GPU driver. |
| No desktop in the shipped image | The image runs `h713-tv`, a fixed HDMI-input service, not a compositor - the projector's job here is the HDMI input. The KMS device (`card1`) is a normal DRM device underneath; nothing stops you from running a compositor on it instead ([docs/subsystems/display.md](subsystems/display.md)). *Superseded on the `medien` branch (15./16.10.2026, no release yet):* an image built with `--profile media,desktop` carries Kodi, a labwc desktop and Firefox as modes the remote's launcher starts, drawn by `h713-warp` as Wayland clients while `h713-tv` stays the only master ([h713-desktop](tools/h713-desktop.md), `doku/212`, `doku/213`); the base image is unchanged. |
| The console keyboard is off while a picture stands | Since seatd runs without a VT (16.10.2026) nobody switches tty1 away from the keys, so a key of the remote or of a USB keyboard would reach the hidden login on tty1 as well as the client. `h713-tv` therefore switches tty1's keyboard off (`K_OFF`) while the ring, a client or an opaque page is on the panel and gives it back with the console (`doku/213` §1) |
| No temperature reading | This unit has no NTC: both of the device's own decompiled device trees say `ntc_num = 0`, and the vendor code treats that as binding rather than fabricating a value (confirmed 2026-09-11, `doku/60` "Der NTC war ein Phantom", patch `0152`). Heat protection runs off the **tachometer** instead - a stalled fan powers the device off (patch `0159`), the same trigger the vendor firmware uses, and the one signal here that is verified (PB5 off -> 0 RPM, on -> 4770-4860 RPM, measured on different days; `board-mgr.md`). A board variant that does carry an NTC picks it up automatically through `ntc_num`. A device that overheats with a *turning* fan is covered by nothing, so keep the vents clear. |
| The projector waits for the power key after being plugged in | Same as with the stock firmware, and deliberate: U-Boot waits in its gate at 2.9 W, silent, since an image runs the vendor ARISC firmware (22.10.2026). Where the boot chain starts crust (an image built with the standby) the remote's power key wakes it too, and it waits at about 0.3 W (measured over FEL on the HY300PRO-G-EU, `doku/191`), but the power supply hums there (TODO 2.42): [docs/uboot/power-gate.md](uboot/power-gate.md). `fw_setenv h713_gate 0` makes it boot on power instead. |
| `brightness` moves the black level, not the picture | The control writes the picture path's black-level offset (register `0x05001234`, read back following the control on 22.09.2026). On bright content that is invisible, on dark content it shows. It is the vendor's own meaning for this field, and `h713-pq` documents which register each control owns. |
| A source the firmware's table does not carry gets the console | The display firmware's mode table is the list of what locks. A raster outside it is refused and named from the firmware's own record (kernel `0171`), without the "change in flight" of older images: on 02.10.2026 a laptop's 1600x1200 read `1600x1200p60, 162.0 MHz not in the firmware's table`, with one journal line, and the picture came back within two seconds of switching to 1080p60. *Superseded 17.10.2026 on the `medien` branch (no release yet):* with h713-osd running, the wall shows the opaque page "No signal on HDMI / HOME: menu" instead of the console for this case too, and for no signal at all ([h713-tv](tools/h713-tv.md), "No signal as a page"); the console stays for `h713-tv ctl off` (the service) and for an image without h713-osd. |
| Setting the EDID block mask publishes nothing by itself | The mask (in-kernel `arisc_hdmi_edid_mask()`, device tree `allwinner,edid-version-mask`, debugfs `edid-version`) stores a byte in the ARISC firmware; the firmware applies it when it next uploads an EDID, at the last fragment. Measured twice on the device, with and without the race that patch `0091e` closes. The default mask 0 is what ships, so port 0 keeps block 0. To make a changed mask visible, trigger a full upload afterwards ([arisc.md](subsystems/arisc.md)). |

## Untested paths

| Path | State |
|---|---|
| Installer on Windows | Not tried for this release; the documentation says so explicitly. `sunxi-fel.exe` for Windows is planned after feedback from Linux users (decision 2026-09-12, `doku/116` section 2). Since layout v4 (2026-09-16) `install` is Linux-only in any case: it mounts the image's own file systems to copy your device's files into them, and says so in one sentence. `identify`, `dump` and `extract` mount nothing. |
| The image's files are copied in through a mount | Layout v4 (2026-09-16, after issue #1): the installer no longer writes the proprietary files into placeholders of a measured size but mounts `hy310-boot` and `hy310-rootfs` and copies them in as ordinary files, so a firmware whose files are bigger than the HY310's fits. Covered by tests that mount a real ext4 and read every file back, including through this project's own ext4 reader, and **accepted on the HY310 on 16.09.2026**: reinstall without a dump, files copied in through the mount, cold start, camera, Wi-Fi, HDMI hot plug. An image built for the old layout is refused by this installer with one sentence, and a v4 image likewise by the installer of its own release; use the installer that ships with the image you have. |

## Feature gaps

| Missing | Detail |
|---|---|
| No sounds of its own | Since `v0.96-beta` the DSP mixes the box's own sounds into HDMI (`hw:hy310hdmi,0`, ALSA's default; [audio](subsystems/audio.md)), measured within 0.07 dB of the HDMI level. Nothing in the image plays one yet - no click on the settings page, no confirmation tone. |
| No standby in the release image, and crust only as an experiment | An image runs the vendor ARISC firmware from the owner's dump and switches off into the power gate: 2.9 W, LED red, silent. From there the power key on the projector starts the next boot, not the remote: the gate reads that key alone. The owner decided so on 22.10.2026 for the HY310 and the HY300PRO-G-EU: with crust, our ARISC firmware, the power supply hums or whines in standby (2.0 W) and when off through crust (0.3 W), and a night with a microphone at the supply found no crust change that is quiet at the same power (TODO 2.42, [arisc](subsystems/arisc.md#crust-experimental)). crust stays in the image: `h713-arisc set crust` brings its 0.3 W power-off, an image built with `--standby` the standby ([h713-arisc](tools/h713-arisc.md)). ## The image on your device may not match a fresh build

Everything built before 2026-09-12 20:00 - the development builds of that week, long before the beta
releases - carries a BL31 (TF-A firmware) from 2026-09-10 with debug assertions still compiled in
(49,260 bytes). The build script never rebuilt it because `make` considered the existing binary current;
a clean build produces the intended release BL31 at 45,164 bytes, four bytes of which are just the
embedded build time. `release/build-all.sh` now wipes the TF-A and U-Boot build directories first, so
this is fixed in the source, and the release BL31 has been on the device since 2026-09-15
(STATUS.md "Boot chain"; `doku/116` section 4a P3.9). Only images built before 2026-09-12 still carry the old one.

Details: `doku/61-todo.md`, `doku/60-offen.md`.
