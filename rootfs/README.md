# `rootfs/` - the Debian 13 recipe

The root filesystem the image carries, built from a package list and an overlay rather than
captured from a running machine: same inputs, same tree, every time (the file modes are fixed by `build-rootfs.sh`, not taken from the umask of the checkout).

| File | What it is |
|---|---|
| `build-rootfs.sh` | the build. `mmdebstrap --variant=minbase` for Debian 13 (trixie, arm64), the packages of `packages.txt` on top, then `install-projekt.sh`. Writes `hy310-rootfs.tar` (what the installer unpacks and what the NFS root is made of), a manifest and checksums, and with `--image-size` an `.ext4` as well |
| `packages.txt` | one package per line, `#` comments. The rule of the file: every line has to trace back to a need written down in the project, no package "just in case". Among them `ping`, `curl`, `wget` and `nc`, so a device can answer "is the network up" from its own end of the cable |
| `packages-media.txt`, `packages-desktop.txt` | the two profiles of `build-rootfs.sh --profile media\|desktop[,..]`: the players, GStreamer with its `va` and `v4l2codecs` decoders and PipeWire (`media`), a compositor, Kodi, a terminal and Firefox (`desktop`), on top of `packages.txt`. Not part of the base image |
| `equivs/` | five control files, built into dummy packages by `build-rootfs.sh` (`dpkg-deb`): `libgbm1`, `libegl-mesa0`, `libgl1-mesa-dri`, `mesa-libgallium`, `libglx-mesa0`. They stand in for Debian's mesa packages, so that Debian's compositors and Kodi install against our mesa and not against `libllvm19` |
| `install-projekt.sh` | everything of ours that goes into an unpacked tree: the overlay, the kernel modules, `h713-tv` and the other device tools, the units. Usable on its own against an existing tree (`./install-projekt.sh /srv/h713-rootfs`), which is how the NFS root on the bench is refreshed |
| `overlay/` | the files that are simply copied in: `etc/fstab`, `etc/network/interfaces`, the zram and journald settings, the sshd drop-in, `etc/h713/`, the udev rules, and the device scripts under `usr/local/sbin` |
| `overlay-va/` | the VA-API wiring that profiles `media` **and** `desktop` lay (`build-rootfs.sh` lays it before the profile's own overlay): `/etc/environment.d/h713-media.conf` (`LIBVA_DRIVER_NAME`, `LIBVA_DRIVERS_PATH`, `GST_VA_ALL_DRIVERS`), `/etc/profile.d/h713-media.sh` (login shells read the same file) and the unit drop-in `/usr/local/share/h713/systemd/h713-media-env.conf` (`EnvironmentFile=`; symlink it into `<unit>.service.d/` for cage, Kodi and the like - system units read neither environment.d nor profile.d) |
| `overlay-media/` | what profile `media` alone lays over `overlay/`: `/etc/mpv/mpv.conf` (`vo=gpu`, `hwdec=vaapi`, cheap settings, the profile `av1-10bit`), the one-line x64 shader that profile loads, and `/etc/wireplumber/wireplumber.conf.d/50-h713.conf` (the DSP bridge as the default sink, no video monitors) and the masks of the PipeWire user units (`etc/systemd/user/pipewire.service`, `pipewire.socket`, `wireplumber.service`, `filter-chain.service` -> `/dev/null`): the packages pull in a systemd user manager and Debian enables those units for every user, so without the masks any login except root's would start PipeWire next to Kodi; start it by hand when a player needs it |
| `overlay-desktop/` | what profile `desktop` alone lays over `overlay/`: `h713-kodi.service` (cage with Kodi in it as a Wayland client of h713-warp's server, not wanted by anything; runs as the system user `h713-kodi` - not root - from `usr/lib/sysusers.d/h713-kodi.conf`, groups `video render audio`, `StateDirectory` as HOME, sandboxed like h713-warp, with `polkitd` and one narrow rule (`etc/polkit-1/rules.d/50-h713-kodi.rules`) so that Kodi's own Suspend/Shut down/Restart entries work for that user and nothing else; `BindsTo=h713-warp.service`, the start sets `h713-tv ctl source auto` through `h713-kodi-switch source` - the client before the ring, the ring back by itself however Kodi ends, no ExecStopPost - h713-tv and h713-warp keep running - the keystone, the overlays and the volume keys stay; `/usr/local/sbin/h713-kodi-switch quit` asks Kodi to quit cleanly; this profile's image starts h713-tv on `source = auto`, so a restart of h713-tv keeps Kodi on the panel), its drop-in `h713-kodi.service.d/10-h713-media-env.conf` (a symlink to the VA-API wiring block of `overlay-va/`), Kodi's starting settings `var/lib/h713-kodi/.kodi/userdata/guisettings.xml` (ALSA `default` = the DSP bridge, JSON-RPC on localhost, no web server) and its keymap `userdata/keymaps/h713-power.xml` (the power key does nothing in Kodi, it is h713-power's; the volume keys neither, they are h713-keys'). A standby ends Kodi before the sleep and starts it again after the wake (`h713-sleep-pre`/`-post`), so no Kodi picture stands on the panel after the wake. Package H2 adds the two other client modes the same way: `h713-desktop.service` (labwc with `etc/h713/labwc/`: rc.xml, menu.xml, autostart with a terminal) and `h713-browser.service` (Firefox maximized in a labwc of its own, `etc/h713/labwc-browser/`, profile prefs in `var/lib/h713-desktop/firefox/user.js`; both run as the system user `h713-desktop`, `usr/lib/sysusers.d/h713-desktop.conf`), their VA-API drop-ins, and the launcher entries `etc/h713/launcher.d/25-browser.conf` and `30-desktop.conf` (`docs/tools/h713-desktop.md`) |
| `libva/` | `build-libva.sh` and `patches/`: megi's `libva-v4l2_request` 1.2 (GPL-3.0) with Christopher Stenger's nine H713 patches and eight of our own (`0010`-`0017`), cross-built with clang against the arm64 sysroot into one module, `usr/local/lib/dri/v4l2_request_drv_video.so` (about 150 KiB, links libc only). The VA-API driver stock ffmpeg, mpv, GStreamer `va*dec` and Kodi use to decode on cedrus (and on the AV1 core, which is switched off in the kernel at present). `build-rootfs.sh --libva` lays the tarball in with profile `media` and with profile `desktop`; the base image does not carry it. The tarball also carries what GPL-3 section 6 calls the Corresponding Source (megi's tree at the pinned commit, the patches, the build script) next to the licence text under `usr/local/share/doc/libva-v4l2-request/` |
| `tests/` | checks that run on the device, not here: `h713-wifi-check.sh` |
| `mesa/` | `build-mesa.sh` and the meson cross file: mesa 25.0.7 with the panfrost driver, EGL (as a glvnd vendor library), GLES2, GBM and the Wayland platform, cross-built with clang against the arm64 sysroot, no LLVM, no X11 - 14 MiB under `/usr/local` instead of Debian's 187 MiB. `libEGL.so.1` and `libGLESv2.so.2` are Debian's glvnd dispatchers (`libegl1`, `libgles2`). `build-rootfs.sh --mesa` lays the tarball in (`--mesa none` leaves the GPU userspace out). The tarball carries mesa's licence texts and a note on where the source is, under `usr/local/share/doc/mesa/` (mesa is MIT: the notice has to travel with every copy). For the GPU and keystone path (`docs/subsystems/video.md`). |

It is built inside the container `h713-build` like everything else - nothing is built on the host -
and `release/build-all.sh` calls it as step 7. Building it by hand is only useful for a bench root;
for an image, take [BUILDING.md](../BUILDING.md).

The result is about 242 MiB, journal in RAM by default, SSH key-only, and it carries no proprietary
file at all: the display, ARISC and Wi-Fi firmware come off your own device while installing
([PROVENANCE.md](../PROVENANCE.md)).
