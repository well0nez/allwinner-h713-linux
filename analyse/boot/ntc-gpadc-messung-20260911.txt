=== Nachtrag 11.09. spaetabends: ch1 ist KEINE Temperatur (gemessen) ===
Gemessen wurde das Datenregister direkt (0x02009084), nicht ueber IIO.

  Ruhe        raw=1445   CPU 54,0 C
  Last  60 s  raw=1509   CPU 69,8 C
  Last 120 s  raw=1516   CPU 71,0 C
  Last 180 s  raw=1514   CPU 71,8 C
  2 s nach Last aus   raw=1447   CPU 59,7 C
  15 s                raw=1445   CPU 56,6 C
  60 s                raw=1444   CPU 54,5 C

Zwei Gruende, warum das keine Temperatur sein kann:
  1. Der Wert springt in 2 s von 1514 auf 1447 zurueck, waehrend die CPU Minuten
     zum Abkuehlen braucht. Keine thermische Masse kuehlt so schnell ab.
  2. Die Richtung ist verkehrt: bei Last STEIGT der Wert. Bei einem NTC muesste
     er nach der Tabelle fallen.
Das Verhalten passt zur CPU-Kernspannung (DVFS: Last -> hoeherer Takt -> hoehere
VDD_CPU -> hoeherer Wert, beim Lastende sofort zurueck).

=== ABER: Marcos Gegenargument (11.09.), das schwerer wiegt ===
Das Geraet hat nachweislich einen Ueberhitzungsschutz: bei Stock schaltet es ab,
wenn man den Luefter entfernt. Es MUSS also einen funktionierenden Fuehler geben.

Und der Kanal stimmt: alle drei Stock-Geraetebaeume (extracted/sun50i-h713-hy310.dts
Zeile 1726, extracted/bootpkg-full.dts 2977, hy310_factory.dts 2697) tragen
uebereinstimmend  ntc0 { enable=1; source=1; channel=1; }.

Daraus folgt: der Fehler liegt NICHT im Kanal und NICHT am fehlenden Fuehler,
sondern in der KONFIGURATION des GPADC-Blocks. Der Mainline-Treiber
sun20i-gpadc-iio.c initialisiert ihn offenbar anders als der Hersteller, sodass
der Wandler etwas anderes als den Eingang misst.

=== AUFLOESUNG (11.09., spaetabends): es gibt keinen NTC ===
Der Hersteller sagt es im Geraetebaum selbst:  ntc_num = 0
  hy310_factory.dts Zeile 2696, extracted/bootpkg-full.dts Zeile 2975
  (beide vom Geraet dekompiliert, nicht von uns geschrieben)

ntc_num ist bindend, nicht dekorativ:
  ntc_read       c05db9a0  Messschleife laeuft ueber ntc_num, bricht bei 0 sofort ab
  avdtemp_read   c05d9700  cmp ntc_num,#0 -> moveq r2,#0x63  (99 = "kein Fuehler")
  ledtemp_read   c05d8ef4  cmp ntc_num,#1 -> movls r2,#0x63  (zweiter Fuehler)
Die ntc0/ntc1-Unterknoten werden bei ntc_num = 0 nie erreicht; ihr enable = 1
ist eine Karteileiche aus der Vorlage.

Damit erklaert sich jede Messung oben:
  - GPADC ch1 ist ein OFFENER Eingang. Deshalb laeuft er mit steigender
    Abtastzeit auf Vollausschlag (Leckstrom laedt den Haltekondensator) und
    folgt sonst der CPU-Last (Uebersprechen/DVFS).
  - GPADC ch0 ist nicht freigeschaltet.
  - Der LRADC ist an diesem Geraet die TASTATUR (allwinner,keyboard_1350mv,
    key_cnt = 6, Schwellen 0 / 0xb1 / 0x158 ...), Vollausschlag 63 heisst
    schlicht "keine Taste gedrueckt". Der lradc-table im Luefterknoten ist
    Vorrat fuer Varianten, die den Fuehler dort haben.

Der Ueberhitzungsschutz haengt am TACHOMETER, nicht am NTC:
  fan_io_status_read  c05d8900  bei anhaltendem Stillstand -> kernel_power_off
  ntc_read            c05db9a0  bei Uebertemperatur -> nur Uevent + record_exception
Ein Stock-Geraet schaltet also ab, wenn man den Luefter entfernt, auch ohne
Fuehler. Der Tacho ist auf diesem Geraet nachgewiesen (PB5 aus -> 0 RPM,
wieder an -> 4770 RPM).

Unser Fehler: hy310-board-mgr hat ntc_num bewusst uebergangen
("Tolerant parsing" in Patch 0008) und aus dem offenen Eingang eine Temperatur
gebaut -- 0, dann 60, dann 71 Grad. Behoben mit Patch 0152.
